Quantum computing is progressing, and its implications for cryptography are well understood. Post-quantum cryptography addresses a concrete near-term threat: it is possible to collect encrypted internet traffic today, in order to decrypt it once sufficiently capable quantum computers become available. This pattern is known as _harvest now, decrypt later_.

Not all cryptographic operations are equally exposed.

*Authentication* (verifying that you are talking to the right server) is less urgent: forging a certificate requires a quantum computer operating in real time at connection time, not one that runs years later on recorded traffic. It will become vulnerable once quantum computers powerful enough to break the asymmetric cryptography used in certificates exist. NIST plans to deprecate classical signature algorithms in 2030 and enforce a hard ban in 2035, though no one can guarantee that sufficiently capable quantum computers will not appear before that.

*Key exchange* (the step where two parties agree on a shared secret over a public channel) is a pressing matter, because recorded traffic is already being harvested today.

Similarly, collected *encrypted messages* could in theory be broken in the future. In practice, the AES-128 cipher used in TLS 1.3 default cipher suites such as `TLS_AES_128_GCM_SHA256` is generally considered adequate for post-quantum security. No action is required on this front.

Since key exchange is already vulnerable to harvest-now-decrypt-later attacks, it is the cryptographic aspect on which this guide, as well as our contributions, focus.

Post-quantum cryptography is a broad field. It covers key exchange (agreeing on a shared secret), digital signatures (proving identity), each addressed by different algorithms with different urgency profiles. This guide focuses specifically on post-quantum *key exchange in TLS*: the step in the TLS handshake where the client and server agree on a session secret. Post-quantum digital signatures (used for certificate authentication and for signing tokens such as JWTs) are separate efforts not covered here.

This guide explains the relevant background on TLS and key exchange, describes the post-quantum algorithm now standardized as the replacement (X25519MLKEM768), and explains how it is supported in Quarkus, regardless of JDK version.

== Background on TLS and cryptography

A TLS session combines three cryptographic mechanisms: key exchange to establish a shared secret, authentication to verify the identity of the server (and optionally the client, in mTLS), and symmetric encryption to encode application data once the handshake is complete.

In link:https://en.wikipedia.org/wiki/Transport_Layer_Security#TLS_1.3[TLS 1.3], these three mechanisms are orchestrated in a single round trip. The client sends a `ClientHello` containing its supported key exchange groups along with an initial key share for its preferred group. The server replies with a `ServerHello` that selects a group and contributes its own key share; both sides can then independently derive the same shared secret.

The server immediately uses that secret to encrypt the rest of its handshake messages, and sends its certificate together with a signature over the transcript, proving ownership of the private key associated with the certificate. The client verifies the certificate against its trust store and checks the signature, completing authentication.

From that point on, all application data is encrypted with AES using a symmetric key derived from the shared secret (link:https://www.rfc-editor.org/info/rfc8446/#section-4[RFC 8446, section 4]).

image::tls_13_handshake.svg[TLS 1.3 handshake overview, align="center"]

This section covers each mechanism in turn.

=== Symmetric cryptography: how to encrypt messages

The internet is a massively distributed network whose very nature makes it difficult to control who will read the packets we send. Thus, the challenge of cryptography is to encode a message so that only the intended receiver can decode it. This is achieved using a _symmetric_ key: a set of bits used to encode and decode messages using a specific algorithm.

A client and a server can communicate securely over an untrusted network as long as they share a common secret `symmetricKey`. They use two methods, `encodeMessage(String message, String key)` and `decodeMessage(String encodedMessage, String key)`, to encode and decode a message using their common symmetric key. Those methods are built to ensure that it is computationally infeasible to reconstruct `message` from `encodedMessage` without knowing the key. The current implementation of this encoding is known as the link:https://www.nist.gov/publications/advanced-encryption-standard-aes[Advanced Encryption Standard (AES)].

This is the basis of modern cryptography but it relies on a non-trivial situation: the client and the server _must each possess the same secret symmetric key_. In some specific situations we could imagine that such a key is hard-coded in both peers, making it possible to communicate with each other. However, the internet is made of billions of devices and the list is ever-evolving. Cryptography must hence tackle another challenge: processes should be able to agree on a _common secret symmetric key_ while exchanging only public information that every other device would be able to see, without being able to construct the same key. This is the role of _asymmetric cryptography_.

=== Asymmetric cryptography: how to agree on a secret

This step is known as _key exchange_ and the protocols as _key exchange groups_, _named groups_, or _supported groups_ in modern TLS.

Several protocols exist for two peers to agree on a common symmetric key, with Elliptic-Curve Diffie-Hellman (ECDH) the dominant one. This section presents classical Diffie-Hellman (DH) as the baseline because of its lower complexity.

The structural principle is the following: each party holds a private value, publishes a derived public value, and independently combines their own private with the other's public to reconstruct a shared secret. This principle also underlies its successors, such as ECDH, which operates over elliptic curve groups rather than integers modulo a prime.

==== Private and public information

The following table summarizes what information is publicly sent on the network and what information is kept private within a peer.

[cols="1,1", options="header"]
|===
| Public information | Private information

| `p`, `g`, `pubKeyC`, `pubKeyS`
| `privKeyC`, `privKeyS`
|===

* `p` and `g` are numbers chosen with specific properties to make it as hard as possible to retrieve the private key from the public key. They are often predefined in the protocol.

* `privKeyC` is the private key generated by the client.
* `privKeyS` is the private key generated by the server.
* `pubKeyC` is the public key derived from `privKeyC`, `p` and `g` by the client.
* `pubKeyS` is the public key derived from `privKeyS`, `p` and `g` by the server.

If the server agrees, the client generates `privKeyC` and `pubKeyC`, and sends only `pubKeyC` to the server. The server then generates `privKeyS` and `pubKeyS`, and sends only `pubKeyS` to the client.

Public and private keys are combined so that there exist a function `f` such that `f(p, g, privKeyC, pubKeyS) = f(p, g, privKeyS, pubKeyC) = secret`. In other words, both the client and the server can agree on a private common secret by executing a function `f` requiring their own private key and the public key of their peer.

Once both peers have built `secret` privately, they can use it as a symmetric encryption key.

Building the shared secret requires not only knowing the public information sent over an untrusted network but also the private key that is *never sent on the network*. Thus, a third party cannot know what `secret` the client and server agreed upon without knowing at least the private key of one of them.

The current dominant key exchange protocol is *X25519*, an implementation of Elliptic-Curve Diffie-Hellman, a successor of Classical Diffie-Hellman presented in the next section.

==== Classical Diffie-Hellman example

The client generates a random number, its _private key_ `privKeyC`, and derives a _public key_ `pubKeyC` from it. `p` is a prime number and `g` is a primitive root modulo `p`. The underlying mathematics are not detailed here; the goal is to highlight how the client and the server are able to construct a private common secret by mixing public and private information.

Mathematically, `pubKeyC = g^privKeyC mod p`.

The server does the same operation, generating `privKeyS` and deriving `pubKeyS = g^privKeyS mod p`.

Finally, the client computes...

----
secretC
= pubKeyS^privKeyC mod p
= (g^privKeyS mod p)^privKeyC mod p
= g^(privKeyS*privKeyC) mod p
----

...and the server computes...

----
secretS
= pubKeyC^privKeyS mod p
= (g^privKeyC mod p)^privKeyS mod p
= g^(privKeyC*privKeyS) mod p
= secretC
----

...and both computations yield the same result.

image::dh.svg[Diffie-Hellman key exchange overview, align="center"]

The mathematical hardness making it intractable for modern supercomputers to find `privKey` from `pubKey` is the _discrete logarithm problem_: given `pubKey`, `g`, and `p`, finding `x` such that `g^x mod p = pubKey` is hard to solve. Certain attacks against it exist: the *Index Calculus* algorithm and the *General Number Field Sieve* enable finding `x` in sub-exponential time. Keys must be quite large (2048 bits or 4096 bits) to remain secure.

For that reason, Classical Diffie-Hellman is now deprecated in favor of Elliptic-Curve Diffie-Hellman (ECDH), which applies the same structural principle over elliptic curve groups: the elliptic curve plays the role of `p` (defining the mathematical space in which operations occur), and a publicly known generator point `G` plays the role of `g`.

Private keys are scalars and public keys are points on the curve derived via scalar multiplication by `G`. The discrete logarithm problem becomes finding the scalar `privKey` given the public point and `G`, which is computationally infeasible for classical computers. In modern TLS, ECDH is used with an elliptic curve named Curve25519, and the protocol is known as *X25519*.

Cracking the private key becomes finding `x` such that `pubKey = x * G`. `x * G` on Curve25519 really means repeated point addition: adding `G` to itself uses the tangent to the curve at `G`, and each subsequent addition of two distinct points uses the secant line through them. In both cases the result is found by reflecting the line's third intersection with the curve across the x-axis, yielding a new point on the curve. This operation is repeated `x` times, and the resulting point is `pubKey`.

No algorithm able to crack ECDH with Curve25519 in sub-exponential time is known, and keys can thus be significantly smaller than those required by classical Diffie-Hellman: a 256-bit ECDH key is more secure than a 2048-bit classical DH key.

=== Authentication

A process should be able to ensure that it is talking to the intended peer. To this end, processes can authenticate themselves using _certificates_. A certificate contains the server's public key and is signed by a trusted Certificate Authority (CA) using the CA's private key. When a client connects, it verifies that signature using the CA's public key, which comes pre-installed on the client (in the OS or browser trust store).

The signature scheme (typically RSA or ECDSA) relies on similar mathematical hardness assumptions as key exchange: deducing a private key from a public key is computationally infeasible for classical computers. This means certificate authentication is also asymmetric cryptography, and is also prone to quantum computer attacks. However, harvest now, decrypt later is not applicable to digital certificates, making quantum-resistant certificates a distant need.

== Quantum computers and cryptography

Quantum computers pose a threat to both symmetric and asymmetric cryptography. Both attacks are described in the next sections.

=== Attacking symmetric cryptography: Grover's algorithm

link:https://en.wikipedia.org/wiki/Grover%27s_algorithm[Grover's algorithm] is a quantum search algorithm that finds a target element in an unsorted list in O(N^1/2^) steps instead of O(N).

In other words, a spy could record encrypted conversations and break the symmetric key used to encode them faster. An n-bit key could be brute-forced in 2^n/2^ operations, compared to the 2^n^ operations required by traditional brute-force attacks. AES keys are effectively "halved" by this attack, and a switch to AES-256 from AES-128 still provides 128-bit post-quantum security, which is considered sufficient.

=== Attacking asymmetric cryptography: Shor's algorithm

In X25519, the public key is derived from the private key, Curve25519, and `G`, a point on Curve25519. It is virtually impossible for today's supercomputers to reverse this operation and deduce the private key from a public key, but quantum computers are able to do so.

link:https://en.wikipedia.org/wiki/Shor%27s_algorithm[Shor's algorithm] can solve the elliptic curve discrete logarithm problem (finding `privKeyC` given `pubKeyC`, Curve25519, and `G`) in polynomial time on a quantum computer, compared to the exponential time required by classical computers.

One could thus record the traffic today, and store `pubKeyC`, and `pubKeyS`. When a sufficiently powerful quantum computer becomes available, one could use it to find `privKeyC` from `pubKeyC`, Curve25519, and `G`. Knowing `privKeyC`, it would be able to compute `secret = f(Curve25519, G, privKeyC, pubKeyS)`, and thus decode the entire conversation between the client and the server.

[cols="1,1,1,1", options="header"]
|===
| Job | Algorithm today | Quantum attack | Urgency

| Symmetric encryption
| AES-128
| link:https://en.wikipedia.org/wiki/Grover%27s_algorithm[Grover's algorithm] halves key strength
| Low — AES-128 (`TLS_AES_128_GCM_SHA256`) is generally considered adequate

| Key exchange
| X25519 (ECDH)
| link:https://en.wikipedia.org/wiki/Shor%27s_algorithm[Shor's algorithm] breaks it in polynomial time
| High — harvest now, decrypt later applies today

| Authentication
| RSA / ECDSA
| link:https://en.wikipedia.org/wiki/Shor%27s_algorithm[Shor's algorithm] breaks it in polynomial time
| Low — requires a real-time capable quantum computer
|===

== Quantum-resistant asymmetric cryptography

Considering that current key exchange protocols (Elliptic-Curve Diffie-Hellman) will be broken by capable-enough quantum computers, new protocols based on different mathematical problems have been proposed and adopted as standards.

_ML-KEM-768_ is the standardized scheme providing quantum-resistant key encapsulation.

=== Key exchange or key encapsulation?

Contrary to X25519, which is a key exchange mechanism, ML-KEM-768 is a _Key Encapsulation Mechanism_ (KEM): the common private key is not constructed by both the server and the client based on the parameters they exchanged and their private keys. Instead:

. the client generates a private decapsulation key `dk` and a public encapsulation key `ek`, then sends `ek` to the server;
. the server generates a secret `s`, encrypts it using `ek`, and sends the resulting ciphertext `ct` to the client;
. the client decapsulates `ct` using its private decapsulation key `dk` and finds `s`.

image::mlkem768.svg[ML-KEM-768 key encapsulation overview, align="center"]

The next section provides mathematical details about ML-KEM-768 to describe how the cryptographic tools used for encapsulating and decapsulating the secret differ from those of DH-based protocols.

=== Mathematical details about ML-KEM-768

As seen previously, the mathematical hardness of X25519 relies on the elliptic curve discrete logarithm problem: it is infeasible for classical computers to find `privKey` from `pubKey` when `pubKey = privKey * G`, with `privKey * G` representing the `privKey`-times repetition of adding the point `G` to itself on Curve25519.

ML-KEM-768 relies on an entirely different mathematical problem: the *learning with errors* problem.

The client generates a matrix `A`, and two vectors `s` and `e`. It then computes `t = A*s+e`.

The public encapsulation key `ek` is the tuple `(A,t)` and the private decapsulation key `dk` is `s`.

`A`, `s`, and `e` are not plain integers but polynomials with integer coefficients, and all arithmetic is done modulo a prime `q`.

The 768 in ML-KEM-768 is associated with the dimension of these polynomial vectors: a larger dimension increases both key size and the hardness of the problem, similar to choosing a larger prime `p` in classical Diffie-Hellman. ML-KEM-512, ML-KEM-768, and ML-KEM-1024 are the three standardized variants, offering increasing security levels at the cost of larger keys and ciphertexts.

Cracking `dk` amounts to finding `s` such that `t = A*s+e`. `e`, the "error" parameter designed to make the private key harder to crack, is not shared, and thus unknown to an attacker. This error element makes the system resistant: without it, solving `t = A*s` is a linear system solvable by Gaussian elimination; the noise introduced by `e` prevents this.

=== X25519MLKEM768

X25519 has been around for decades and guarantees security against classical computers. ML-KEM-768 is new, and mathematical weaknesses may be discovered in the future. The National Institute of Standards and Technology (NIST) opted for a combined use of both protocols. The client and the server build two secrets: one using X25519 and the other using ML-KEM-768. These secrets are concatenated and a symmetric key is derived from the result to encode every communication. The derivation ensures that if at least one of the input secrets is secure, the output is secure as well. The resulting protocol is naturally named *X25519MLKEM768*.

image::x25519mlkem768.svg[X25519MLKEM768 hybrid key exchange overview, align="center"]

== Supporting PQC in Quarkus

On JDK 25 (October 2026 Critical Patch Update or later) and JDK 27+, X25519MLKEM768 is negotiated by default: no configuration is required. The `pqc-enforcement-policy` property is not needed to enable PQC; it is there to guarantee the use of post-quantum key exchange groups (rejecting peers that do not support it) and to fail fast at startup if the runtime ends up without a PQC-capable engine.

For JDK 17 and 21, PQC requires OpenSSL 3.5+ via `smallrye-openssl`. X25519MLKEM768 will be backported to those versions according to the link:https://www.java.com/en/jre-jdk-cryptoroadmap.html[Oracle JRE and JDK Cryptographic Roadmap]; dates may change.

Quarkus therefore supports PQC via two mechanisms:

* using the JDK default SSL engine for JDK 25 (October 2026 Critical Patch Update or later) and JDK 27+
* using the OpenSSL engine for JDK 17 and 21

This was also an opportunity to have proper SSL engine selection in Quarkus, as using OpenSSL over JdkSSL can result in better performance. Vert.x HTTP servers being the underlying stack of Quarkus, the integration began in Vert.x.

=== Vert.x integration

Vert.x already had a way to leverage OpenSSL using link:https://github.com/netty/netty-tcnative[*netty-tcnative*] (`io.netty:netty-tcnative`), a JNI bridge that allows Netty to delegate TLS operations to a native SSL library, bypassing the JDK's built-in SSL implementation.

Netty-tcnative ships in several variants: statically linked (the native library is bundled inside the JAR) and dynamically linked (it links against a native library installed on the host at runtime), each available for OpenSSL, LibreSSL, and BoringSSL.

The static OpenSSL version is too old (1.1.1) and does not support PQC. A dynamic OpenSSL variant also exists, acting as a thin JNI mapping between the `netty-tcnative-classes` Java API and the host OpenSSL library. However, this variant was compiled against OpenSSL 1.x headers. OpenSSL 3.x is not a drop-in replacement: loading the 1.x-compiled `.so` against a 3.x host library causes a runtime crash. Relinking is not sufficient, the C sources must be recompiled against the 3.x headers.

`netty-tcnative-openssl-dynamic` was therefore rebuilt against OpenSSL 3.x, and published as link:https://github.com/smallrye/smallrye-openssl[smallrye-openssl] on Maven Central. This gives Vert.x users access to OpenSSL 3.5+ features, including post-quantum algorithms, without any changes to the Java API surface.

[discrete]
===== Requirements

To use OpenSSL, the user needs:

* Linux x86_64 or Linux aarch64 only: `smallrye-openssl` does not ship native binaries for macOS, Windows, IBM Power (ppc64le), IBM Z (s390x), or Alpine Linux
* OpenSSL 3.5+ on the host machine
* `libapr-1` on the host machine, a library required by netty-tcnative
* a dependency on `netty-tcnative-classes` in their project
* a dependency on the platform-specific `smallrye-openssl` classifier artifact in their project

=== Quarkus integration

Quarkus uses a centralized mechanism for specifying TLS-related properties: the `TlsConfigurationRegistry` class. Properties are declared in `application.properties` and propagated to the underlying TLS stack.

Three properties control post-quantum key exchange:

`quarkus.tls.key-exchange-groups`::
A comma-separated list of key exchange groups to advertise during the TLS handshake (for example, `X25519MLKEM768`). If the active SSL engine does not support at least one group in the list, the application fails at startup.

`quarkus.tls.pqc-enforcement-policy`::
Controls how strictly the application requires post-quantum key exchange. Accepts `relaxed`, `client-negotiated`, or `strict`.

`quarkus.tls.ssl-engine`::
Selects the SSL engine: `jdkssl` or `openssl`. When omitted and `pqc-enforcement-policy` is `client-negotiated` or `strict`, the engine is selected automatically as described below.

==== JVM mode vs. native mode

The configuration described above applies to *JVM mode*. In JVM mode, both SSL engine paths are available: OpenSSL via `smallrye-openssl` on any supported JDK, and JdkSSL on JDK 25 (October 2026 Critical Patch Update or later) and JDK 27+.

In *native mode*, the OpenSSL path is not available. The `smallrye-openssl` JNI bridge loads a native `.so` at runtime, which is incompatible with GraalVM native image's closed-world assumption. JdkSSL is the only engine available in a native executable, and its PQC support depends on the JDK version integrated in Mandrel, the GraalVM distribution used to build Quarkus native images. PQC will be available in native mode once a future Mandrel release ships based on a JDK version that includes X25519MLKEM768.

== Conclusion

The rise of quantum computers threatens the security of TLS not only in a few years but also today: existing key exchange protocols such as X25519 are prone to harvest-now-decrypt-later attacks. Consequently, new post-quantum standards such as X25519MLKEM768 have been adopted to ensure that communications cannot be collected today and decrypted when a sufficiently capable quantum computer becomes available.

OpenSSL integrates these new schemes in its version 3.5, and in Java starting with JDK 25 (October 2026 Critical Patch Update) and JDK 27+. The Java team is working to backport the integration to JDK 17 and 21, expected in the first half of 2027 according to the link:https://www.java.com/en/jre-jdk-cryptoroadmap.html[Oracle JRE and JDK Cryptographic Roadmap]; dates may change.

Due to the pressing nature of harvest-now-decrypt-later attacks, Quarkus had to integrate PQC in Java 21 before January 2027. To that end, `netty-tcnative` was used for Vert.x, the underlying engine of Quarkus, to leverage OpenSSL 3.5+ and benefit from PQC.
