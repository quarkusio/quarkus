= Enable post-quantum key exchange in a Quarkus application
include::_attributes.adoc[]
:categories: security
:diataxis-type: howto
:summary: Enable post-quantum key exchange (X25519MLKEM768) in a Quarkus application using the pqc-enforcement-policy property, covering JDK 17/21 via OpenSSL, JDK 25/27+ via JdkSSL, and mTLS.
:topics: security, TLS, cryptography, pqc, post-quantum
:extensions: io.quarkus:quarkus-tls-registry

Enable post-quantum key exchange in a Quarkus application to protect TLS connections against harvest-now-decrypt-later attacks.
For background on how X25519MLKEM768 works and how Quarkus integrates it, see xref:post-quantum-key-exchange.adoc[Post-Quantum Key Exchange in Quarkus].

== Prerequisites

Depending on your Java version, one of the two setups below is required.

[NOTE]
====
The OpenSSL path is JVM-only. Native mode is not supported when relying on `smallrye-openssl` for PQC; use JDK 27+ for native image builds.
====

[discrete]
===== Java 17 / 21

* OpenSSL 3.5+ installed on the host machine
* `libapr-1` installed on the host machine (on UBI-based container images: `microdnf install -y apr`)
* `netty-tcnative-classes` and `smallrye-openssl` dependencies in `pom.xml`:

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.netty</groupId>
    <artifactId>netty-tcnative-classes</artifactId>
</dependency>
<!-- native library, pick the classifier matching your platform -->
<dependency>
    <groupId>io.smallrye</groupId>
    <artifactId>smallrye-openssl</artifactId>
    <version>{smallrye-openssl-version}</version>
    <classifier>linux-x86_64</classifier>  <!-- or linux-aarch_64 -->
</dependency>
----

[discrete]
===== Java 25 (October 2026 Critical Patch Update or later) and Java 27+

No additional dependencies required.

== Step 1: Bootstrap the server

Create a basic Quarkus REST application using the Quarkus CLI or Maven.

[source,bash,role="primary asciidoc-tabs-target-sync-cli asciidoc-tabs-target-sync-maven"]
.CLI
----
quarkus create app org.acme:pqc-server \
    --extension='rest'
cd pqc-server
----

[source,bash,role="secondary asciidoc-tabs-target-sync-maven",subs=attributes+]
.Maven
----
mvn {quarkus-platform-groupid}:quarkus-maven-plugin:{quarkus-version}:create \
    -DprojectGroupId=org.acme \
    -DprojectArtifactId=pqc-server \
    -Dextensions='rest'
cd pqc-server
----

Before enabling PQC, the server must serve HTTPS. Generate a self-signed certificate and keystore:

[source,bash]
----
keytool -genkeypair -alias server -keyalg EC -keysize 256 \
  -storetype PKCS12 -keystore src/main/resources/server-keystore.p12 \
  -validity 3650 -storepass password \
  -dname "CN=localhost, OU=Test, O=Test, L=Test, ST=Test, C=US"
----

Add the following to `src/main/resources/application.properties`:

[source,properties]
----
quarkus.http.ssl-port=8443
quarkus.http.insecure-requests=disabled
quarkus.tls.key-store.p12.path=server-keystore.p12
quarkus.tls.key-store.p12.password=password
----

The `GreetingResource` generated by the scaffold is already a suitable test endpoint:

[source,java]
----
@Path("/hello")
public class GreetingResource {
    @GET
    @Produces(MediaType.TEXT_PLAIN)
    public String hello() {
        return "Hello from Quarkus REST";
    }
}
----

== Step 2: Bootstrap the client

Create a second Quarkus application that will act as the REST client.

[source,bash,role="primary asciidoc-tabs-target-sync-cli-client asciidoc-tabs-target-sync-maven-client"]
.CLI
----
quarkus create app org.acme:pqc-client \
    --extension='rest-client,rest'
cd pqc-client
----

[source,bash,role="secondary asciidoc-tabs-target-sync-maven-client",subs=attributes+]
.Maven
----
mvn {quarkus-platform-groupid}:quarkus-maven-plugin:{quarkus-version}:create \
    -DprojectGroupId=org.acme \
    -DprojectArtifactId=pqc-client \
    -Dextensions='rest-client,rest'
cd pqc-client
----

If the client runs on JDK 17 or 21, it needs the same OpenSSL 3.5+, `libapr-1`, and Maven dependencies as the server. PQC key exchange must be supported by the SSL engine on both ends of the handshake:

[source,xml,subs=attributes+]
----
<dependency>
    <groupId>io.netty</groupId>
    <artifactId>netty-tcnative-classes</artifactId>
</dependency>
<!-- native library, pick the classifier matching your platform -->
<dependency>
    <groupId>io.smallrye</groupId>
    <artifactId>smallrye-openssl</artifactId>
    <version>{smallrye-openssl-version}</version>
    <classifier>linux-x86_64</classifier>  <!-- or linux-aarch_64 -->
</dependency>
----

The scaffold generates a default `GreetingResource`. Delete it and create two new files under `src/main/java/org/acme/`.

`src/main/java/org/acme/GreetingClient.java` - a typed REST client interface that maps to the server endpoint:

[source,java]
----
package org.acme;

import org.eclipse.microprofile.rest.client.inject.RegisterRestClient;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

@RegisterRestClient(baseUri = "https://localhost:8443")
public interface GreetingClient {
    @GET
    @Path("/hello")
    @Produces(MediaType.TEXT_PLAIN)
    String hello();
}
----

`src/main/java/org/acme/ClientResource.java` - a REST endpoint that invokes the client and returns the result:

[source,java]
----
package org.acme;

import org.eclipse.microprofile.rest.client.inject.RestClient;
import jakarta.inject.Inject;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

@Path("/client")
public class ClientResource {
    @Inject
    @RestClient
    GreetingClient greetingClient;

    @GET
    @Produces(MediaType.TEXT_PLAIN)
    public String hello() {
        return greetingClient.hello();
    }
}
----

Since the server uses a self-signed certificate, export it and import it into the client's truststore so the TLS handshake can succeed:

[source,bash]
----
keytool -exportcert -alias server \
  -keystore ../pqc-server/src/main/resources/server-keystore.p12 \
  -storetype PKCS12 -storepass password -rfc \
  -file server.crt

keytool -importcert -alias server -file server.crt \
  -keystore src/main/resources/client-truststore.p12 \
  -storetype PKCS12 -storepass password -noprompt
----

Add the truststore configuration to `src/main/resources/application.properties`:

[source,properties]
----
quarkus.http.port=8081
quarkus.tls.client.trust-store.p12.path=client-truststore.p12
quarkus.tls.client.trust-store.p12.password=password
quarkus.rest-client."org.acme.GreetingClient".tls-configuration-name=client
----

`quarkus.tls.client.*` creates a *named* TLS configuration called `client` in the TLS registry. The `default` name is only registered when the application itself serves HTTPS. Since the client app has no TLS server, `default` does not exist. The REST client then references the named config via `tls-configuration-name`; without that line it sets up its own SSL context independently and ignores the registry entirely.

== Step 3: Relaxed policy - baseline behavior

With both applications running in their default state, TLS is negotiated using classical key exchange groups. Explicitly set the enforcement policy on the server to `relaxed` to confirm the baseline:

[source,properties]
----
# pqc-server/src/main/resources/application.properties
quarkus.tls.pqc-enforcement-policy=relaxed
----

Start both applications and trigger the client:

[source,bash]
----
# Terminal 1 - server
cd pqc-server && ./mvnw quarkus:dev

# Terminal 2 - client
cd pqc-client && ./mvnw quarkus:dev

# Terminal 3 - test
curl http://localhost:8081/client
# → Hello from Quarkus REST
----

The connection succeeds as expected. Under `relaxed`, the server imposes no constraint on the key exchange group negotiated with the client. Classical groups such as X25519 are accepted.

[NOTE]
====
On JDK 25 (October 2026 Critical Patch Update or later) and JDK 27+, X25519MLKEM768 is negotiated even without an enforcement policy. A server with no policy will still fall back to classical groups with a client that does not support PQC; `strict` turns that fallback into a hard failure at handshake time. Both `strict` and `client-negotiated` also fail at startup if no PQC-capable engine is available, surfacing misconfiguration early.
====

== Step 4: Client-negotiated policy

`client-negotiated` is the recommended first step for a real deployment. The server advertises PQC groups and uses them with clients that support PQC, but falls back to classical key exchange with clients that do not. Existing peers are not disrupted.

Switch the server policy to `client-negotiated`:

[source,properties]
----
# pqc-server/src/main/resources/application.properties
quarkus.tls.pqc-enforcement-policy=client-negotiated
----

Restart the server, then trigger the client again:

[source,bash]
----
curl http://localhost:8081/client
# → Hello from Quarkus REST
----

The connection succeeds. A PQC-capable client negotiates X25519MLKEM768; a classical client negotiates a classical group and is still accepted.

== Step 5: Strict policy - locking out classical peers

[WARNING]
====
`strict` rejects any peer that does not advertise PQC groups. On a *server*, this includes older clients, health checks, and load balancers that do not support PQC. On a *client*, this causes connection failures against any server that does not support PQC, including third-party APIs. Only use `strict` when all peers are known to support PQC.
====

Switch the server policy to `strict`:

[source,properties]
----
# pqc-server/src/main/resources/application.properties
quarkus.tls.pqc-enforcement-policy=strict
----

Trigger the client again:

[source,bash]
----
curl http://localhost:8081/client
# → HTTP 500 - javax.net.ssl.SSLHandshakeException: ...
----

The client fails to connect. The server now only accepts connections using PQC-compliant key exchange groups. The default Quarkus client does not advertise PQC groups, so the server rejects it.

Set the same policy on the client side:

[source,properties]
----
# pqc-client/src/main/resources/application.properties
quarkus.tls.client.pqc-enforcement-policy=strict
----

Trigger the client again:

[source,bash]
----
curl http://localhost:8081/client
# → Hello from Quarkus REST
----

The connection is restored. Both sides now advertise and negotiate X25519MLKEM768, and the TLS handshake completes using a quantum-resistant key exchange.

A Wireshark capture shows that the client offered X25519MLKEM768 (1184 bytes for the ML-KEM-768 encapsulation key plus 32 bytes for X25519, totaling 1216 bytes):

----
Extension: key_share (len=1222) X25519MLKEM768
    Type: key_share (51)
    Length: 1222
    Key Share extension
        Client Key Share Length: 1220
        Key Share Entry: Group: X25519MLKEM768, Key Exchange length: 1216
            Group: X25519MLKEM768 (4588)
            Key Exchange Length: 1216
            Key Exchange [...]: .......
----

The ServerHello key share confirms the group was selected. The server's share is 1120 bytes (1088 bytes for the ML-KEM-768 ciphertext plus 32 bytes for X25519):

----
Extension: key_share (len=1124) X25519MLKEM768
    Type: key_share (51)
    Length: 1124
    Key Share extension
        Key Share Entry: Group: X25519MLKEM768, Key Exchange length: 1120
            Group: X25519MLKEM768 (4588)
            Key Exchange Length: 1120
            Key Exchange [...]: .......
----

[NOTE]
====
To inspect the TLS handshake in detail directly from a Quarkus application, the link:https://github.com/quarkiverse/quarkus-network-capture[Quarkus Network Capture] extension (requires Quarkus 4) captures network traffic without requiring an external tool.
====

For fine-grained control over which groups are advertised or which engine is used, see the `key-exchange-groups` and `ssl-engine` properties described in xref:post-quantum-key-exchange.adoc#quarkus-integration[Post-Quantum Key Exchange in Quarkus].

== Enabling PQC in mTLS

In mutual TLS, both the client and the server authenticate each other using certificates, in addition to the standard server-only authentication. From a post-quantum perspective, mTLS introduces no additional complexity: the key exchange step is identical to regular TLS and X25519MLKEM768 is negotiated the same way regardless of whether mutual authentication is required.

The `pqc-enforcement-policy`, `key-exchange-groups`, and `ssl-engine` properties apply without modification.

The certificate-based mutual authentication step uses classical signature schemes (RSA or ECDSA) on both sides. As discussed in the introduction, forging a certificate signature requires a quantum computer operating in real time, which is a future concern rather than an immediate one.

Post-quantum signature schemes (such as ML-DSA) exist and are standardized, but migrating certificate authentication is a separate effort outside the scope of this guide.

In practice, enabling PQC in a Quarkus mTLS setup requires only the same configuration changes described above, applied to both client and server.
