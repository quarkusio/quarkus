= Modularity SPI reference
include::_attributes.adoc[]
:diataxis-type: reference
:extension-status: experimental
:summary: Reference for the build items that Quarkus extensions use to participate in Quarkus modularity.
:topics: modularity,jpms,modules,extensions,spi

This document describes the build items that extension authors use to integrate with the xref:modularity.adoc[Quarkus modularity] system.
Extensions can declare boot modules, add inter-module dependencies, and consume the completed module model.
Explicit module descriptors retain their declared package access, including qualified exports and opens.
When the optional `ModulePackages` attribute is absent, Quarkus discovers package names from class files while preserving the descriptor's access rules.
For the dynamic module loader, an open module is represented by opening each packaged package; boot module descriptors retain the open-module flag.

include::{includes}/extension-status.adoc[]

== `BootModulePathBuildItem`

`BootModulePathBuildItem` is a `MultiBuildItem` produced by extensions.
It declares that a named module must be placed on the boot module path.

An extension should produce this item when it provides a module that must be in the JDK's boot module layer.
This is necessary when the module is required before the dynamic module loader (`smallrye-modules`) starts, or when the module must participate in the boot class loading chain.

The constructor takes a single `String` parameter: the module name.

[source,java]
----
@BuildStep
BootModulePathBuildItem myBootModule() {
    return new BootModulePathBuildItem("com.example.my.boot.module");
}
----

The modularity extension computes the transitive closure of all declared boot modules.
If a boot module depends on other modules (via `LINKED` dependencies), those modules are also included in the boot set automatically.
Automatic modules are excluded from the boot set because they cannot be linked by `jlink`.

== `AddDependencyBuildItem`

`AddDependencyBuildItem` is a `MultiBuildItem` produced by extensions.
It adds a dependency between two modules at build time.

An extension should produce this item when it needs to wire a module dependency that is not expressed in the Maven POM or in the module's `module-info.class` descriptor.
This is common when Quarkus extensions generate code that references types from another module, or when service loading relationships must be declared explicitly.

The constructor takes three parameters: the source module name (`String`), the target module name (`String`), and a set of dependency modifiers (`Modifiers<Dependency.Modifier>`).

[source,java]
----
@BuildStep
AddDependencyBuildItem extraDependency() {
    return new AddDependencyBuildItem(
        "com.example.source.module",
        "com.example.target.module",
        Dependency.Modifier.set(Dependency.Modifier.LINKED, Dependency.Modifier.READ));
}
----

When multiple items declare the same source/target pair, their modifier sets are merged.

== `ApplicationModuleInfoBuildItem`

`ApplicationModuleInfoBuildItem` is a `SimpleBuildItem` produced by the modularity extension.
It contains the completed `AppModuleModel`, which includes the module descriptor for every module in the application, the set of boot modules, and the set of JDK modules in use.

This item is consumed by downstream packaging extensions such as the xref:jlink.adoc[jlink extension].
Extension authors generally do not need to consume this item unless they are implementing a custom packaging step.

== Dependency modifiers

The `Dependency.Modifier` enum (from `io.smallrye.modules.desc`) defines the following values.
These are used with `AddDependencyBuildItem` to control how the dependency is wired.

`LINKED`::
The dependency is linked for class loading.
Classes from the target module are visible to the source module's class loader.

`READ`::
The dependency is readable from the source module.
Exported packages from the target module are accessible to the source module.

`SERVICES`::
Service implementations in the target module are available to the source module via `ServiceLoader`.

`OPTIONAL`::
The dependency is optional.
If the target module is not present at link time, the dependency is silently ignored rather than causing a failure.

`TRANSITIVE`::
The dependency is transitive.
Any module that depends on the source module also implicitly depends on the target module.

`SYNTHETIC`::
The dependency was added by a framework rather than declared in the original module descriptor. _Note:_ because modifier sets are merged when a dependency is declared in two places, this modifier would take precedence over a non-synthetic dependency, which is a minor detail but possibly undesirable. Thus, this modifier may change to be "non-synthetic" or something along those lines in the final version, so that an explicit dependency will never be marked as being synthetic.

`MANDATED`::
The dependency is mandated by specification (for example, the implicit dependency on `java.base`).

== Related core build items

The `quarkus-core-deployment` module provides three additional build items that affect the module graph.
These are documented separately but are noted here for completeness.

`ModuleOpenBuildItem` declares that one module should open specified packages to another module (equivalent to the `--add-opens` JVM flag).
`ModuleExportBuildItem` declares that one module should export specified packages to another module (equivalent to the `--add-exports` JVM flag).
During dynamic module reconfiguration in dev and test modes, packages absent from the source module are ignored without warnings.
It also supplies native-image builder exports (`-J--add-exports`).
The builder loads application libraries and generated features from the classpath, so their target module names are mapped to `ALL-UNNAMED`, just as for fast-jar runners.

Extension authors should migrate from the deprecated `JPMSExportBuildItem` to `ModuleExportBuildItem`, specifying the module that needs access to the exported packages.
Version bounds on legacy `JPMSExportBuildItem` instances are ignored.

`ModuleEnableNativeAccessBuildItem` declares that a module requires native access (equivalent to the `--enable-native-access` JVM flag).

== Generated class placement

`GeneratedClassPlacementBuildItem` in `quarkus-modular-spi` assigns a generated class to a module without requiring its producer to discover module names:

[source,java]
----
placements.produce(GeneratedClassPlacementBuildItem.inModuleOf(bridgeName, hostName));
placements.produce(GeneratedClassPlacementBuildItem.inApplication(bootstrapName));
----

The class must also be produced as a `GeneratedClassBuildItem`.
The anchor can be an existing runtime class or another generated class.
Placement controls the packaged class bytes and the destination module's packages, including newly generated packages.
Generated classes without a placement declaration retain package-based assignment: they follow the module owning their package, or the application module for an unclaimed package.
This also applies when an explicit placement introduces a new package.

Missing anchors, conflicting placements, cyclic placement relationships, and ambiguous class ownership fail the build.
Explicit placement cannot introduce split packages while package-based resource routing remains in use.
Placement into an existing owner of an already split package is allowed; unrelated generated classes in that package retain their existing routing.
These declarations affect modular packaging only; they do not change the meaning of `GeneratedClassBuildItem.isApplicationClass()` or dev-mode class loading.

== Class-based access

`ClassAccessBuildItem` describes access requirements using class names instead of module names:

[source,java]
----
accesses.produce(ClassAccessBuildItem.direct(generatedReaderName, hostName));
accesses.produce(ClassAccessBuildItem.reflective(accessContextName, memberDeclaringClassName));
----

Modularity resolves both classes after generated-class placement.
`direct` adds class loading linkage and readability (`LINKED`, `READ`, and `SYNTHETIC`), together with a qualified export of the target package to the caller's module.
`reflective` adds readability and a qualified open of the declaring package, without adding class loading linkage.
The reflective caller must already have the reflected class or member, or obtain it using an appropriate class loader.
Both declarations grant access to an entire package, not just the named class, and direct access still obeys Java member visibility.
Duplicate requirements are merged; opens take precedence over exports, and same-module requirements need no additional access.

Caller classes must belong to application runtime artifacts or generated classes; target classes can additionally belong to system modules of the build JDK.
JDK class ownership is resolved without loading the class.
JDK callers and placement of generated classes in JDK modules are rejected because these declarations cannot modify JDK module contents or dependencies.
Classes in placement and access declarations, including placement anchors, must belong to a named package; the default package is unsupported by named modules.
Class-based declarations are consumed by modular packaging; existing core module access items remain available for requirements that also apply to other packaging and launch modes.

Ownership checks are batched by artifact and reuse the package inventory needed for modular packaging.
Only classes required by the declarations and their generated-class placement relationships are checked; modularity does not retain a class ownership index of every runtime dependency.
When a package is split between artifacts, the class resource is checked in each candidate artifact to determine its owner.
