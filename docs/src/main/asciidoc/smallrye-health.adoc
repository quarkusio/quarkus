= Add health checks to a Quarkus application with SmallRye Health
include::_attributes.adoc[]
:summary: Report whether a Quarkus application is running and ready to serve requests with liveness, readiness, and startup health checks.
:topics: health,observability
:extensions: io.quarkus:quarkus-smallrye-health

To report whether a Quarkus application is running and ready to serve requests, add the `quarkus-smallrye-health` extension and write health checks as CDI beans.

The extension exposes the health endpoints as soon as you add it.
In cloud environments, automated processes call these endpoints to decide whether to send the application requests, restart it, or replace it.
If the application also uses an extension that generates Kubernetes resources, such as `quarkus-kubernetes` or `quarkus-openshift`, the generated resources use these endpoints for their liveness and readiness probes.
They also use the startup endpoint for a startup probe, except on Knative.

https://github.com/smallrye/smallrye-health/[SmallRye Health] implements the https://github.com/eclipse/microprofile-health/[MicroProfile Health] specification.

[id="liveness-readiness-and-startup-checks"]
== Liveness, readiness, startup, and wellness checks

Each health check reports `UP` or `DOWN`, and its annotation decides which endpoint reports it and what a `DOWN` result causes.
To choose the annotation, find the question that your check answers in the following table.

[cols="3,1,2,3",options="header"]
|===
|Question that the check answers |Annotation |Endpoint |What Kubernetes does when the probe for the endpoint fails

|Is the application broken in a way that only a restart fixes, for example, a deadlock?
|`@Liveness`
|`/q/health/live`
|Restarts the container.

|Can the application serve requests right now, for example, can it reach its database?
|`@Readiness`
|`/q/health/ready`
|Stops routing Service traffic to the application until the endpoint reports `UP` again.

|Has an application that starts slowly finished starting?
|`@Startup`
|`/q/health/started`
|Runs no liveness or readiness probe until the endpoint reports `UP`.
If the probe keeps failing, restarts the container.

|Does the check report a condition that you want to watch, but that no probe acts on?
|`@Wellness`
|`/q/health/well`
|Nothing, because no generated probe uses this endpoint.
|===

Choose by what a `DOWN` result causes, not by what the check tests.
A database that is down makes a database check report `DOWN`, but restarting the application does not bring the database back, so a database check is a readiness check.
If it were a liveness check, Kubernetes would restart the application repeatedly while the database is down.
The Kubernetes documentation says that liveness probes must indicate unrecoverable application failure, and that incorrect liveness probes can lead to cascading failures.
For details, see https://kubernetes.io/docs/concepts/workloads/pods/probes/[Liveness, Readiness, and Startup Probes].

Quarkus applications start quickly, so most of them do not need a startup check.
The https://github.com/eclipse/microprofile-health/[MicroProfile Health] specification describes the liveness, readiness, and startup checks.
Wellness checks are an experimental SmallRye Health feature: the specification does not cover them, and they are subject to change.

Every health endpoint returns a JSON object with two fields:

* `status`: the overall result of the checks that the endpoint reports.
* `checks`: an array with one entry per check.
Each entry has a `name`, a `status`, and, if the check adds any, a `data` object.

The overall `status` is `UP` only when every check that the endpoint reports is `UP`.
When it is `DOWN`, the endpoint returns the HTTP status 503 (Service Unavailable).

[id="additional-endpoints"]
== Additional endpoints

Besides the four endpoints that report one type of check each, the extension exposes the following endpoints:

`/q/health/group/<name>`::
Reports the checks in the health group `<name>`.
To put a check in a group, annotate it with `@HealthGroup("<name>")`.
A health group is not a type of check.
A check can carry the annotation alone or next to a type annotation.
With a type annotation, the endpoint for that type reports the check too.

`/q/health/group`::
Reports the checks in all health groups.

`/q/health`::
Reports the liveness, readiness, startup, and wellness checks together.
A check that only has a `@HealthGroup` annotation is not part of it.

Health groups are an experimental SmallRye Health feature: the MicroProfile Health specification does not cover them, and they are subject to change.
For an example, see <<group-health-checks>>.

[id="creating-your-first-health-check"]
== Add a liveness check

A liveness check reports whether the application is broken in a way that only a restart fixes, for example, a deadlock.
Write it as a CDI bean that implements the `HealthCheck` interface and carries the `@Liveness` annotation, and the `/q/health/live` endpoint reports it.

Create the `org.acme.microprofile.health.SimpleHealthCheck` class:

[source,java]
----
package org.acme.microprofile.health;

import jakarta.enterprise.context.ApplicationScoped;

import org.eclipse.microprofile.health.HealthCheck;
import org.eclipse.microprofile.health.HealthCheckResponse;
import org.eclipse.microprofile.health.Liveness;

@Liveness
@ApplicationScoped <1> <2>
public class SimpleHealthCheck implements HealthCheck {

    @Override
    public HealthCheckResponse call() {
        return HealthCheckResponse.up("Simple health check");
    }
}
----
<1> Annotate the health check class with `@ApplicationScoped` or `@Singleton`, so that one bean instance serves all health check requests.
<2> If a bean class annotated with one of the health check annotations declares no scope, the `@Singleton` scope is used automatically.

`HealthCheck` is a functional interface.
Its single method, `call`, returns a `HealthCheckResponse`, which `HealthCheckResponse.up(String)` builds in one call.

With the application running in dev mode, request the liveness endpoint:

[source,bash]
----
curl http://localhost:8080/q/health/live
----

In a project with no other liveness checks, the response is:

[source,json]
----
{
    "status": "UP",
    "checks": [
        {
            "name": "Simple health check",
            "status": "UP"
        }
    ]
}
----

[id="adding-a-readiness-health-check-procedure"]
== Add a readiness check

A readiness check reports whether the application can process requests, for example, whether it can reach its database.
Annotate the check with `@Readiness`, and the `/q/health/ready` endpoint reports it.

The following check stands in for a database connection check and always reports `UP`.
Create the `org.acme.microprofile.health.DatabaseConnectionHealthCheck` class:

[source,java]
----
package org.acme.microprofile.health;

import jakarta.enterprise.context.ApplicationScoped;

import org.eclipse.microprofile.health.HealthCheck;
import org.eclipse.microprofile.health.HealthCheckResponse;
import org.eclipse.microprofile.health.Readiness;

@Readiness
@ApplicationScoped
public class DatabaseConnectionHealthCheck implements HealthCheck {

    @Override
    public HealthCheckResponse call() {
        return HealthCheckResponse.up("Database connection health check");
    }
}
----

With the application running in dev mode, request the readiness endpoint:

[source,bash]
----
curl http://localhost:8080/q/health/ready
----

The response lists the `Database connection health check` with the status `UP`.
The liveness endpoint, `/q/health/live`, does not list it, because the check has the `@Readiness` annotation only.
The `/q/health` endpoint lists it together with the checks of the other types.

[id="adding-a-startup-health-check-procedure"]
== Add a startup check

A startup check reports whether an application that starts slowly has finished starting.
Annotate the check with `@Startup`, and the `/q/health/started` endpoint reports it.

NOTE: Import the `org.eclipse.microprofile.health.Startup` annotation, not `io.quarkus.runtime.Startup`, which has the same simple name.

Create the `org.acme.microprofile.health.StartupHealthCheck` class:

[source,java]
----
package org.acme.microprofile.health;

import jakarta.enterprise.context.ApplicationScoped;

import org.eclipse.microprofile.health.HealthCheck;
import org.eclipse.microprofile.health.HealthCheckResponse;
import org.eclipse.microprofile.health.Startup;

@Startup
@ApplicationScoped
public class StartupHealthCheck implements HealthCheck {

    @Override
    public HealthCheckResponse call() {
        return HealthCheckResponse.up("Startup health check");
    }
}
----

With the application running in dev mode, request the startup endpoint:

[source,bash]
----
curl http://localhost:8080/q/health/started
----

The response lists the `Startup health check` with the status `UP`.
The `/q/health` endpoint also lists it.

[id="negative-health-check-procedures"]
== Report a `DOWN` status

A health check reports `DOWN` when the condition that it tests fails, for example, when the application cannot reach its database.
To set the status at run time, build the response with a `HealthCheckResponseBuilder`.

The following readiness check reports `DOWN` unless the `database.up` configuration property is `true`.
The property stands in for a real database connection test.
Create the `org.acme.microprofile.health.DatabaseConnectionHealthCheck` class, or replace it if it exists:

[source,java]
----
package org.acme.microprofile.health;

import jakarta.enterprise.context.ApplicationScoped;

import org.eclipse.microprofile.config.inject.ConfigProperty;
import org.eclipse.microprofile.health.HealthCheck;
import org.eclipse.microprofile.health.HealthCheckResponse;
import org.eclipse.microprofile.health.HealthCheckResponseBuilder;
import org.eclipse.microprofile.health.Readiness;

@Readiness
@ApplicationScoped
public class DatabaseConnectionHealthCheck implements HealthCheck {

    @ConfigProperty(name = "database.up", defaultValue = "false")
    boolean databaseUp;

    @Override
    public HealthCheckResponse call() {

        HealthCheckResponseBuilder responseBuilder = HealthCheckResponse.named("Database connection health check");

        try {
            simulateDatabaseConnectionVerification();
            responseBuilder.up();
        } catch (IllegalStateException e) {
            // cannot access the database
            responseBuilder.down()
                    .withData("error", e.getMessage()); // pass the exception message
        }

        return responseBuilder.build();
    }

    private void simulateDatabaseConnectionVerification() {
        if (!databaseUp) {
            throw new IllegalStateException("Cannot contact database");
        }
    }
}
----

`HealthCheckResponse.up(String)` and `HealthCheckResponse.down(String)` build a response in one call.
`HealthCheckResponse.named(String)` returns a `HealthCheckResponseBuilder` instead, so that the check can set the status after it tests the condition.
When the check fails, it also adds the error message to the response with `withData`.

With the application running in dev mode, request the readiness endpoint:

[source,bash]
----
curl -i http://localhost:8080/q/health/ready
----

The endpoint returns the HTTP status 503, and the overall `status` is `DOWN`:

[source,json]
----
{
    "status": "DOWN",
    "checks": [
        {
            "name": "Database connection health check",
            "status": "DOWN",
            "data": {
                "error": "Cannot contact database"
            }
        }
    ]
}
----

The liveness endpoint, `/q/health/live`, still reports `UP`, because readiness checks do not affect it.

To make the check report `UP` again, add the following line to the `src/main/resources/application.properties` file:

[source,properties]
----
database.up=true
----

In dev mode, the change takes effect at the next request.

[id="adding-user-specific-data-to-the-health-check-response"]
== Add data to a health check response

Besides its name and status, a health check can return key-value pairs, for example, the error that made it fail.
Add them with the `withData(key, value)` method of the response builder.

Create the `org.acme.microprofile.health.DataHealthCheck` class:

[source,java]
----
package org.acme.microprofile.health;

import jakarta.enterprise.context.ApplicationScoped;

import org.eclipse.microprofile.health.HealthCheck;
import org.eclipse.microprofile.health.HealthCheckResponse;
import org.eclipse.microprofile.health.Liveness;

@Liveness
@ApplicationScoped
public class DataHealthCheck implements HealthCheck {

    @Override
    public HealthCheckResponse call() {
        return HealthCheckResponse.named("Health check with data")
                .up()
                .withData("foo", "fooValue")
                .withData("bar", "barValue")
                .build();
    }
}
----

With the application running in dev mode, request the liveness endpoint:

[source,bash]
----
curl http://localhost:8080/q/health/live
----

The entry for the check in the `checks` array includes a `data` object with the pairs:

[source,json]
----
{
    "name": "Health check with data",
    "status": "UP",
    "data": {
        "foo": "fooValue",
        "bar": "barValue"
    }
}
----

Data is most useful when a check fails.
To pass the error along with a `DOWN` status, add it to the builder, for example, `responseBuilder.down().withData("error", e.getMessage())`.

[id="reactive-health-checks"]
== Write a reactive health check

To compute a health check result without blocking, implement the `io.smallrye.health.api.AsyncHealthCheck` interface instead of `HealthCheck`.
Its `call` method returns a `Uni<HealthCheckResponse>`.

The MicroProfile Health specification does not support reactive types, but SmallRye Health does.

The following example shows a reactive liveness check.
Create the `org.acme.microprofile.health.LivenessAsync` class:

[source,java]
----
package org.acme.microprofile.health;

import java.time.Duration;

import jakarta.enterprise.context.ApplicationScoped;

import org.eclipse.microprofile.health.HealthCheckResponse;
import org.eclipse.microprofile.health.Liveness;

import io.smallrye.health.api.AsyncHealthCheck;
import io.smallrye.mutiny.Uni;

@Liveness
@ApplicationScoped
public class LivenessAsync implements AsyncHealthCheck {

    @Override
    public Uni<HealthCheckResponse> call() {
        return Uni.createFrom().item(HealthCheckResponse.up("liveness-reactive"))
                .onItem().delayIt().by(Duration.ofMillis(10));
    }
}
----

With the application running in dev mode, request the liveness endpoint:

[source,bash]
----
curl http://localhost:8080/q/health/live
----

The response lists the `liveness-reactive` check with the status `UP`.

[id="add-a-wellness-check"]
== Add a wellness check

A wellness check reports a condition that you want to watch, but that no probe acts on.
Annotate the check with `@Wellness`, and the `/q/health/well` endpoint reports it.

The `@Wellness` annotation is experimental: the MicroProfile Health specification does not cover it, and it is subject to change.

Create the `org.acme.microprofile.health.WellnessHealthCheck` class:

[source,java]
----
package org.acme.microprofile.health;

import jakarta.enterprise.context.ApplicationScoped;

import org.eclipse.microprofile.health.HealthCheck;
import org.eclipse.microprofile.health.HealthCheckResponse;

import io.smallrye.health.api.Wellness;

@Wellness
@ApplicationScoped
public class WellnessHealthCheck implements HealthCheck {

    @Override
    public HealthCheckResponse call() {
        return HealthCheckResponse.up("Wellness health check");
    }
}
----

With the application running in dev mode, request the wellness endpoint:

[source,bash]
----
curl http://localhost:8080/q/health/well
----

The response lists the `Wellness health check` with the status `UP`.
The `/q/health` endpoint also lists it.

[id="group-health-checks"]
== Group health checks

To report a set of checks on an endpoint of its own, put them in a health group with the `@HealthGroup("<name>")` annotation.
The `/q/health/group/<name>` endpoint reports the checks in that group.

A check in a group can also carry a type annotation, such as `@Liveness`, and then the endpoint for that type reports it too.

The `@HealthGroup` annotation is experimental: the MicroProfile Health specification does not cover it, and it is subject to change.

Create the `org.acme.microprofile.health.ExternalServiceHealthCheck` class:

[source,java]
----
package org.acme.microprofile.health;

import jakarta.enterprise.context.ApplicationScoped;

import org.eclipse.microprofile.health.HealthCheck;
import org.eclipse.microprofile.health.HealthCheckResponse;

import io.smallrye.health.api.HealthGroup;

@HealthGroup("external-services") <1>
@ApplicationScoped
public class ExternalServiceHealthCheck implements HealthCheck {

    @Override
    public HealthCheckResponse call() {
        return HealthCheckResponse.up("External service health check");
    }
}
----
<1> To put the check in more than one group, repeat the annotation with another name.

With the application running in dev mode, request the group endpoint:

[source,bash]
----
curl http://localhost:8080/q/health/group/external-services
----

The response lists the `External service health check` with the status `UP`.
The `/q/health/group` endpoint lists the checks in all groups.
The `/q/health` endpoint does not list the check, because it only belongs to a health group.

[id="health-status-change-observers"]
== React to health status changes

To run code when the health status of the application changes, observe the `io.smallrye.health.event.SmallRyeHealthStatusChangeEvent` CDI event with the standard CDI observer mechanism.

To observe the status of one type, add the `@Liveness`, `@Readiness`, or `@Startup` qualifier from `org.eclipse.microprofile.health`, or the `@Wellness` qualifier from `io.smallrye.health.api`.
To observe the overall status, add `@Default`.
SmallRye Health fires the event only when a status changes.

An observer method can run on the event loop thread instead of a worker thread, so never block in it.

The following observer logs each change:

[source,java]
----
package org.acme.microprofile.health;

import jakarta.enterprise.context.ApplicationScoped;
import jakarta.enterprise.event.Observes;
import jakarta.enterprise.inject.Default;

import org.eclipse.microprofile.health.Liveness;
import org.eclipse.microprofile.health.Readiness;

import io.quarkus.logging.Log;
import io.smallrye.health.event.SmallRyeHealthStatusChangeEvent;

@ApplicationScoped
public class HealthObserver {

    public void observeHealthChange(@Observes @Default SmallRyeHealthStatusChangeEvent event) {
        Log.infof("Health status changed to %s", event.health().getStatus());
    }

    public void observeReadinessChange(@Observes @Readiness SmallRyeHealthStatusChangeEvent event) {
        Log.infof("Readiness status changed to %s", event.health().getStatus());
    }

    public void observeLivenessChange(@Observes @Liveness SmallRyeHealthStatusChangeEvent event) {
        Log.infof("Liveness status changed to %s", event.health().getStatus());
    }
}
----

[id="extension-health-checks"]
== Turn off the health checks that extensions register

Some extensions register their own health checks when you add them.
For example, the `quarkus-agroal` extension, which manages datasources, registers a readiness check that validates each datasource, as described in xref:datasource.adoc#datasource-health-check[Datasource health check].

To register none of the extension health checks, set the following build-time property:

[source,properties]
----
quarkus.smallrye-health.extensions.enabled=false
----

[id="management-interface"]
== Expose health checks on the management interface

By default, the main HTTP server serves the health endpoints.
To serve them on a separate network interface and port, enable the management interface.

Set the following property in your application configuration:

[source,properties]
----
quarkus.management.enabled=true
----

This is a build-time property, so you cannot override its value at runtime.
If the application also uses `quarkus-kubernetes` or `quarkus-openshift`, the generated probes use the management port, except on Knative.

If you enable the management interface without customizing its network interface and port, the health checks are at `http://0.0.0.0:9000/q/health`.
To change the `health` segment of that path, set the `quarkus.smallrye-health.root-path` property.

For more information, see the xref:./management-interface-reference.adoc[management interface reference].
