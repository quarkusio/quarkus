Quantum computing is progressing, and its implications for cryptography are well understood. Post-quantum cryptography addresses a concrete near-term threat: it is possible to collect encrypted internet traffic today, in order to decrypt it once sufficiently capable quantum computers become available. This pattern is known as _harvest now, decrypt later_.

Not all cryptographic operations are equally exposed.

*Authentication* (verifying that you are talking to the right server) is less urgent: forging a certificate requires a quantum computer operating in real time at connection time, not one that runs years later on recorded traffic. It will become vulnerable once quantum computers powerful enough to break the asymmetric cryptography used in certificates exist. NIST plans to deprecate classical signature algorithms in 2030 and enforce a hard ban in 2035, though no one can guarantee that sufficiently capable quantum computers will not appear before that.

*Key exchange* (the step where two parties agree on a shared secret over a public channel) is a pressing matter, because recorded traffic is already being harvested today.

Similarly, collected *encrypted messages* could in theory be broken in the future. In practice, the AES-128 cipher used in TLS 1.3 default cipher suites such as `TLS_AES_128_GCM_SHA256` is generally considered adequate for post-quantum security. No action is required on this front.
Since key exchange is already vulnerable to harvest-now-decrypt-later attacks, it is the cryptographic aspect on which this article, as well as our contributions, focus.

This article explains the relevant background on TLS and key exchange, describes the post-quantum algorithm now standardized as the replacement (X25519MLKEM768), and walks through how to enable it in a Quarkus application today, regardless of JDK version.

== Background on TLS and cryptography

A TLS session combines three cryptographic mechanisms: key exchange to establish a shared secret, authentication to verify the identity of the server (and optionally the client, in mTLS), and symmetric encryption to encode application data once the handshake is complete.

In link:https://en.wikipedia.org/wiki/Transport_Layer_Security#TLS_1.3[TLS 1.3], these three mechanisms are orchestrated in a single round trip. The client sends a `ClientHello` containing its supported key exchange groups along with an initial key share for its preferred group. The server replies with a `ServerHello` that selects a group and contributes its own key share; both sides can then independently derive the same shared secret. The server immediately uses that secret to encrypt the rest of its handshake messages, and sends its certificate together with a signature over the transcript, proving ownership of the private key associated with the certificate. The client verifies the certificate against its trust store and checks the signature, completing authentication. From that point on, all application data is encrypted with AES using a symmetric key derived from the shared secret (link:https://www.rfc-editor.org/info/rfc8446/#section-4[RFC 8446, section 4]).

image::tls_13_handshake.svg[TLS 1.3 handshake overview, align="center"]

This section covers each mechanism in turn.

=== Symmetric cryptography: how to encrypt messages?

Internet is a massively distributed network whose very nature makes it difficult to control who will read the packets we send. Thus, the challenge of cryptography is to encode a message so that only the intended receiver can decode it. This is achieved using a _symmetric_ key: a set of bits used to encode and decode messages using a specific algorithm.
A client and a server can communicate securely over an untrusted network as long as they share a common secret symmetric key `key_sym`. They use two methods, `encodeMessage(String message, String key)` and `decodeMessage(String encodedMessage, String key)`, to encode and decode a message using their common symmetric key. Those methods are built to ensure that it is computationally infeasible to reconstruct `message` from `encodedMessage` without knowing the key. The current implementation of this encoding is known as the link:https://www.nist.gov/publications/advanced-encryption-standard-aes[Advanced Encryption Standard (AES)].

This is the basis of modern cryptography but it relies on a non-trivial situation: the client and the server _must each possess the same secret symmetric key_. In some specific situations we could imagine that such a key is hard-coded in both peers, making it possible to communicate with each other. However, the internet is made of billions of devices and the list is ever-evolving. Cryptography must hence tackle another challenge: processes should be able to agree on a _common secret symmetric key_ while exchanging only public information that every other device would be able to see, without being able to construct the same key. This is the role of _asymmetric cryptography_.

=== Asymmetric cryptography: how to agree on a secret?

This step is known as _key exchange_ and the protocols as _key exchange groups_, _named groups_, or _supported groups_ in modern TLS.
Several protocols exist for two peers to agree on a common symmetric key, with Elliptic-Curve Diffie-Hellman (ECDH) the dominant one. We will present classical Diffie-Hellman (DH) as the baseline because of its lower complexity.
The structural principle is the following: each party holds a private value, publishes a derived public value, and independently combines their own private with the other's public to reconstruct a shared secret. This principle also underlies its successors, such as ECDH, which operates over elliptic curve groups rather than integers modulo a prime.

==== Private and public information

The below table summarizes what information is publicly sent on the network and what information is kept private within a peer.

[cols="1,1", options="header"]
|===
| public information | private information

| `p`, `g`, `pubKeyC`, `pubKeyS`
| `privKeyC`, `privKeyS`
|===

* `p` and `g` are numbers chosen with specific properties to ensure that deducing a private key from a public key is computationally infeasible.
* `privKeyC` is the private key generated by the client.
* `privKeyS` is the private key generated by the server.
* `pubKeyC` is the public key derived from `privKeyC`, `p` and `g` by the client.
* `pubKeyS` is the public key derived from `privKeyS`, `p` and `g` by the server.

The client picks `p` and `g` and sends them to the server on an untrusted network. If the server agrees, the client generates `privKeyC` and `pubKeyC`, and sends only `pubKeyC` to the server. The server then generates `privKeyS` and `pubKeyS`, and sends only `pubKeyS` to the client.

`p` and `g` are chosen so that there exists a function `f` such that `f(p, g, privKeyC, pubKeyS) = f(p, g, privKeyS, pubKeyC) = secret`. In other words, both the client and the server can agree on a private common secret by executing a function `f` requiring their own private key and the public key of their peer.

Once both peers have built `secret` privately, they can use it as a symmetric encryption key.

Building the shared secret requires not only knowing the public information sent over an untrusted network but also the private key that is *never sent on the network*. Thus, a third party cannot know what `secret` the client and server agreed upon without knowing at least the private key of one of them. The current dominant key exchange protocol is *X25519*, an implementation of Elliptic-Curve Diffie-Hellman, a successor of Classical Diffie-Hellman presented in the next section.

==== Classical Diffie-Hellman example

The client generates a random number, its _private key_ `privKeyC`, and derives a _public key_ `pubKeyC` from it. `p` is a prime number and `g` is a primitive root modulo `p`. We don't need to detail the underlying mathematics of Diffie-Hellman for our presentation; we just want to highlight how the client and the server are able to construct a private common secret by mixing public and private information.
Mathematically, `pubKeyC = g^privKeyC mod p`.

The server does the same operation, generating `privKeyS` and deriving `pubKeyS = g^privKeyS mod p`.

Finally, the client computes...

----
secretC
= pubKeyS^privKeyC mod p
= (g^privKeyS mod p)^privKeyC mod p
= g^(privKeyS*privKeyC) mod p
----

...and the server computes...

----
secretS
= pubKeyC^privKeyS mod p
= (g^privKeyC mod p)^privKeyS mod p
= g^(privKeyC*privKeyS) mod p
= secretC
----

...and they get the same result.

image::dh.svg[Diffie-Hellman key exchange overview, align="center"]

The mathematical hardness making it intractable for modern supercomputers to find `privKey` from `pubKey` is the _discrete logarithm problem_: given `pubKey`, `g`, and `p`, finding `x` such that `g^x mod p = pubKey` is hard to solve. Certain attacks against it exist: the *Index Calculus* algorithm and the *General Number Field Sieve* enable finding `x` in sub-exponential time. Keys must be quite large (2048 bits or 4096 bits) to remain secure.

For that reason, Classical Diffie-Hellman is now deprecated in favor of Elliptic-Curve Diffie-Hellman (ECDH), which applies the same structural principle over elliptic curve groups: the elliptic curve plays the role of `p` (defining the mathematical space in which operations occur), and a publicly known generator point `G` plays the role of `g`. Private keys are scalars and public keys are points on the curve derived via scalar multiplication by `G`. The discrete logarithm problem becomes finding the scalar `privKey` given the public point and `G`, which is computationally infeasible for classical computers. In modern TLS, ECDH is used with an elliptic curve named Curve25519, and the protocol is known as *X25519*.

Cracking the private key becomes finding `x` such that `pubKey = x * G`. `x * G` on Curve25519 really means repeated point addition: adding `G` to itself uses the tangent to the curve at `G`, and each subsequent addition of two distinct points uses the secant line through them. In both cases the result is found by reflecting the line's third intersection with the curve across the x-axis, yielding a new point on the curve. This operation is repeated `x` times, and the resulting point is `pubKey`.
No algorithm able to crack ECDH with Curve25519 in sub-exponential time is known, and keys can thus be significantly smaller than those required by classical Diffie-Hellman: a 256-bit ECDH key is more secure than a 2048-bit classical DH key.

=== Authentication

A process should be able to ensure that it is talking to the right peer. To this end, processes can authenticate themselves using _certificates_. A certificate contains the server's public key and is signed by a trusted Certificate Authority (CA) using the CA's private key. When a client connects, it verifies that signature using the CA's public key, which comes pre-installed on the client (in the OS or browser trust store).

The signature scheme (typically RSA or ECDSA) relies on similar mathematical hardness assumptions as key exchange: deducing a private key from a public key is computationally infeasible for classical computers. This means certificate authentication is also asymmetric cryptography, and is also prone to quantum computer attacks. However, harvest now, decrypt later is not applicable to digital certificates, making quantum-resistant certificates a distant need.

== Quantum computers and cryptography

Quantum computers pose a threat to both symmetric and asymmetric cryptography. We detail both attacks in the next sections.

=== Attacking symmetric cryptography: Grover's algorithm

link:https://en.wikipedia.org/wiki/Grover%27s_algorithm[Grover's algorithm] is a quantum search algorithm that finds a target element in an unsorted list in O(N^1/2^) steps instead of O(N).
In other words, a spy could record encrypted conversations and break the symmetric key used to encode them faster. An n-bit key could be brute-forced in 2^n/2^ operations, compared to the 2^n^ operations required by traditional brute-force attacks. AES keys are effectively "halved" by this attack, and a switch to AES-256 from AES-128 still provides 128-bit post-quantum security, which is considered sufficient.

=== Attacking asymmetric cryptography: Shor's algorithm

In X25519, the public key is derived from the private key, `curve25519`, and `G`, a point on `curve25519`. It is virtually impossible for today's supercomputers to reverse this operation and deduce the private key from a public key, but quantum computers are able to do so.
link:https://en.wikipedia.org/wiki/Shor%27s_algorithm[Shor's algorithm] can solve the elliptic curve discrete logarithm problem (finding `privKeyC` given `pubKeyC`, `curve25519`, and `G`) in polynomial time on a quantum computer, compared to the exponential time required by classical computers.
One could thus record the traffic today, and store `curve25519`, `G`, `pubKeyC`, and `pubKeyS`. When a sufficiently powerful quantum computer becomes available, one could use it to find `privKeyC` from `pubKeyC`, `curve25519`, and `G`. Knowing `privKeyC`, it would be able to compute `secret = f(curve25519, G, privKeyC, pubKeyS)`, and thus decode the entire conversation between the client and the server.

[cols="1,1,1,1", options="header"]
|===
| Job | Algorithm today | Quantum attack | Urgency

| Symmetric encryption
| AES-128
| link:https://en.wikipedia.org/wiki/Grover%27s_algorithm[Grover's algorithm] halves key strength
| Low — AES-128 (`TLS_AES_128_GCM_SHA256`) is generally considered adequate

| Key exchange
| X25519 (ECDH)
| link:https://en.wikipedia.org/wiki/Shor%27s_algorithm[Shor's algorithm] breaks it in polynomial time
| High — harvest now, decrypt later applies today

| Authentication
| RSA / ECDSA
| link:https://en.wikipedia.org/wiki/Shor%27s_algorithm[Shor's algorithm] breaks it in polynomial time
| Low — requires a real-time capable quantum computer
|===

== Quantum-resistant asymmetric cryptography

Considering that current key exchange protocols (Elliptic-Curve Diffie-Hellman) will be broken by capable-enough quantum computers, new protocols based on different mathematical problems have been proposed and adopted as standards.
_ML-KEM-768_ is the standardized scheme providing quantum-resistant key encapsulation.

=== Key exchange or key encapsulation?

Contrary to X25519 which is a key exchange mechanism, ML-KEM-768 is a _Key Encapsulation Mechanism_ (KEM): the common private key is not constructed by both the server and the client based on the parameters they exchanged and their private keys. Instead:

. the client generates a private decapsulation key `dk` and a public encapsulation key `ek`, then sends `ek` to the server;
. the server generates a secret `s`, encrypts it using `ek`, and sends the resulting ciphertext `ct` to the client;
. the client decapsulates `ct` using its private decapsulation key `dk` and finds `s`.

image::mlkem768.svg[ML-KEM-768 key encapsulation overview, align="center"]

The next section provides mathematical details about ML-KEM-768 to describe how the cryptographic tools used for encapsulating and decapsulating the secret differ from those of DH-based protocols.

=== Mathematical details about ML-KEM-768

As seen previously, the mathematical hardness of X25519 relies on the elliptic curve discrete logarithm problem: it is infeasible for classical computers to find `privKey` from `pubKey` when `pubKey = privKey * G`, with `privKey * G` representing the `privKey`-times repetition of adding the point `G` to itself on Curve25519.

ML-KEM-768 relies on an entirely different mathematical problem: the *learning with errors* problem.
The client generates a matrix `A`, and two vectors `s` and `e`. It then computes `t = A*s+e`.
The public encapsulation key `ek` is the tuple `(A,t)` and the private decapsulation key `dk` is `s`.

`A`, `s`, and `e` are not plain integers but polynomials with integer coefficients, and all arithmetic is done modulo a prime `q`. The 768 in ML-KEM-768 refers to the dimension of these polynomial vectors: a larger dimension increases both key size and the hardness of the problem, similar to choosing a larger prime `p` in classical Diffie-Hellman. ML-KEM-512, ML-KEM-768, and ML-KEM-1024 are the three standardized variants, offering increasing security levels at the cost of larger keys and ciphertexts.

Cracking `dk` amounts to finding `s` such that `t = A*s+e`. It is worth noting that `e`, the "error" parameter designed to make the private key harder to crack, is not shared. An attacker must hence solve `t-e = A*s` with two unknown values, `s` and `e`. This error element makes the system resistant: without it, solving `t=A*s` is a linear system solvable by Gaussian elimination.

=== X25519MLKEM768

X25519 has been around for decades and guarantees security against classical computers. ML-KEM-768 is new, and mathematical weaknesses may be discovered in the future. The standard opted for a combined use of both protocols. The client and the server build two secrets: one using X25519 and the other using ML-KEM-768. These secrets are concatenated and a symmetric key is derived from the result to encode every communication. The derivation ensures that if at least one of the input secrets is secure, the output is. The resulting protocol is naturally named *X25519MLKEM768*.

image::x25519mlkem768.svg[X25519MLKEM768 hybrid key exchange overview, align="center"]

== Supporting PQC in Quarkus

On JDK 27+, X25519MLKEM768 is negotiated by default: no configuration is required. The `pqc-enforcement-policy` property is not needed to enable PQC; it is there to guarantee it (rejecting peers that do not support it) and to fail fast at startup if the runtime ends up without a PQC-capable engine.

For JDK versions before 27, PQC requires OpenSSL 3.5+ via `smallrye-openssl`. X25519MLKEM768 will be backported to earlier versions according to the link:https://www.java.com/en/jre-jdk-cryptoroadmap.html[Oracle JRE and JDK Cryptographic Roadmap], but Java 21 would not be able to leverage it before January 2027 at the soonest.

Thus, it was decided to add support for PQC in two ways:

* using the JDK default SSL engine for JDK 27 and later
* using the OpenSSL engine for previous versions

This was also an opportunity to have proper SSL engine selection in Quarkus, as using OpenSSL over JdkSSL can result in better performance. Vert.x HTTP servers being the underlying stack of Quarkus, the integration began in Vert.x.

=== Vert.x integration

Vert.x already had a way to leverage OpenSSL using *netty-tcnative*.

==== Netty-tcnative

`netty-tcnative` exists in several variants (OpenSSL, LibreSSL, and BoringSSL), each shipped in both a static form (the crypto library compiled directly into a `.so` bundled inside the JAR) and a dynamic form (the `.so` links against a crypto library present on the host machine at runtime).

The static OpenSSL version is too old (1.1.1) and doesn't support PQC. A dynamic OpenSSL variant also exists, acting as a thin JNI mapping between the `netty-tcnative-classes` Java API and the host OpenSSL library. However, this variant was compiled against OpenSSL 1.x headers. OpenSSL 3.x is not a drop-in replacement: loading the 1.x-compiled `.so` against a 3.x host library causes a runtime crash. Relinking is not sufficient, the C sources must be recompiled against the 3.x headers.

We therefore rebuilt `netty-tcnative-openssl-dynamic` against OpenSSL 3.x and published it as link:https://github.com/smallrye/smallrye-openssl[smallrye-openssl] on Maven Central. This gives Vert.x users access to OpenSSL 3.5+ features, including post-quantum algorithms, without any changes to the Java API surface.

*Requirements*

To use OpenSSL, the user needs:

* Linux x86_64 or Linux aarch64 only: `smallrye-openssl` does not ship native binaries for macOS, Windows, IBM Power (ppc64le), IBM Z (s390x), or Alpine Linux
* OpenSSL 3.5+ on the host machine
* `libapr-1` on the host machine, a library required by netty-tcnative
* a dependency on `netty-tcnative-classes` in their project
* a dependency on `smallrye-openssl` in their project

The table below indicates how PQC is available depending on the JDK version:

[cols="1,2", options="header"]
|===
| Runtime | How PQC is provided

| JDK 27+
| JdkSSL (built-in) or OpenSSL (`smallrye-openssl`)

| JDK 25
| JdkSSL after the October 2026 Critical Patch Update (check your vendor), or OpenSSL (`smallrye-openssl`)

| JDK 17 / 21
| OpenSSL (`smallrye-openssl`) only; JdkSSL backport expected in the first half of 2027
|===

Rows listing OpenSSL require OpenSSL 3.5+ and `libapr-1` on the host, and the `netty-tcnative-classes` and `smallrye-openssl` Maven dependencies listed above. Dates follow the link:https://www.java.com/en/jre-jdk-cryptoroadmap.html[Oracle JRE and JDK Cryptographic Roadmap] and may change.

==== Vert.x API

Three options are relevant when setting PQC in Vert.x:

* *added for PQC* - `SSLOptions setKeyExchangeGroups(List<String> keyExchangeGroups)`
* *added for PQC* - `SSLOptions setPqcEnforcementPolicy(PqcEnforcementPolicy policy)`
* *already in Vert.x* - `TCPSSLOptions setSslEngineOptions(SslEngineOptions engine)`

The first option is self-explanatory: the user specifies a list of key exchange groups they want to use for TLS sessions. If the list is not applicable, typically because the SSL engine doesn't support at least one group of the list, the application crashes and logs an error.

The second option defines how Vert.x will enforce the use of quantum-resistant key exchange groups; it can take three values:

. `RELAXED`: the runtime won't enforce PQ groups.
. `CLIENT_NEGOTIATED`: the server has to support PQ groups but will accept clients who do not support them and use classical key exchange with them.
. `STRICT`: the server has to support PQ groups and will reject clients not supporting PQ groups.

Finally, the third option allows users to specify which SSL engine should be used in the application. It can be left blank, in which case the application defaults to the `JdkSslEngine`. This behavior has been changed as the automatic engine selection has been modified for PQC, as detailed below.

Key exchange groups and PQC enforcement policy work together and are resolved once at startup in `SslEngineUtils.resolveKeyExchangeGroups(List<String> groups, PqcEnforcementPolicy pqcPolicy)` as described by the below table.

[cols="2,2,2,2", options="header"]
|===
| `groups` | `STRICT` | `CLIENT_NEGOTIATED` | `RELAXED` / `null`

| `null` / empty
| *Defaulted* → `PQ_COMPLIANT_GROUPS`
| *Defaulted* → `DEFAULT_KEY_EXCHANGE_GROUPS`
| *Passed through* → `null`/empty

| All PQ-compliant
| *Accepted* → `groups` as-is
| *Accepted* → `groups` as-is
| *Passed through* → `groups` as-is

| Mixed (some PQ-compliant)
| *Overridden* → `PQ_COMPLIANT_GROUPS`
| *Accepted* → `groups` as-is
| *Passed through* → `groups` as-is

| None PQ-compliant
| *Overridden* → `PQ_COMPLIANT_GROUPS`
| *Augmented* → `PQ_COMPLIANT_GROUPS + groups`
| *Passed through* → `groups` as-is
|===

Once groups are resolved according to the policy, SSL engine resolution is performed using `SslContextManager.resolveEngineOptions(SSLEngineOptions engineOptions, boolean useAlpn, PqcEnforcementPolicy pqcPolicy)`. The below table shows how resolution is conducted.

| `STRICT` or `CLIENT_NEGOTIATED`

| engine `isPqcAvailable()` = true
| *Validated* - provided engine kept

| `STRICT` or `CLIENT_NEGOTIATED`
| provided
| engine `isPqcAvailable()` = false
| *Thrown* - engine lacks PQC support

| `STRICT` or `CLIENT_NEGOTIATED`
| `null`
| JDK `isPqcAvailable()` = true
| *Auto-selected* `JdkSSLEngineOptions`

| `STRICT` or `CLIENT_NEGOTIATED`
| `null`
| JDK = false, OpenSSL `isPqcAvailable()` = true
| *Auto-selected* `OpenSSLEngineOptions`

| `STRICT` or `CLIENT_NEGOTIATED`
| `null`
| neither JDK nor OpenSSL support PQC
| *Thrown* - no PQC-capable engine available

| `RELAXED` / `null`
| provided

| `RELAXED` / `null`

=== Quarkus integration

Quarkus uses a centralized method for specifying TLS-related properties: the `TlsConfigurationRegistry` class. Properties are declared in the `application.properties` file and are propagated to the underlying Vert.x server or client. The table below shows the equivalence between Vert.x and Quarkus properties.

[cols="2,1", options="header"]
|===
| Vert.x | Quarkus

| `SSLOptions setKeyExchangeGroups(List<String> keyExchangeGroups)`
| `key-exchange-groups`

| `SSLOptions setPqcEnforcementPolicy(PqcEnforcementPolicy policy)`
| `pqc-enforcement-policy`

| `TCPSSLOptions setSslEngineOptions(SslEngineOptions engine)`
| `quarkus.tls.ssl-engine`
|===

The values expected by these Quarkus properties reflect the parameters expected by the Vert.x methods:

* `key-exchange-groups` takes a comma-separated list of key exchange groups.
* `pqc-enforcement-policy` takes one of three values: `relaxed`, `client-negotiated`, `strict`.
* `ssl-engine` takes one of two values: `jdkssl` or `openssl`.

Key exchange group resolution as well as engine resolution is performed by Vert.x as indicated in the section above. The same prerequisites as Vert.x apply for using OpenSSL.

==== JVM mode vs. native mode

The configuration described above applies to *JVM mode*. In JVM mode, both SSL engine paths are available: OpenSSL via `smallrye-openssl` on any supported JDK, and JdkSSL on JDK 27 or later.

In *native mode*, the OpenSSL path is not available. The `smallrye-openssl` JNI bridge loads a native `.so` at runtime, which is incompatible with GraalVM native image's closed-world assumption. JdkSSL is the only engine available in a native executable, and its PQC support depends on the JDK version integrated in Mandrel, the GraalVM distribution used to build Quarkus native images. PQC will be available in native mode once a future Mandrel release ships based on a JDK version that includes X25519MLKEM768.

== Enabling PQC in a Quarkus application

The following walkthrough demonstrates PQC negotiation step by step using the enforcement policy. On JDK 27+, PQC is already active by default; the policy is introduced to show how to guarantee it and reject peers that do not support it.
The walkthrough is based on the Quarkus link:https://quarkus.io/guides/getting-started/[Getting Started guide].

=== Prerequisites

Depending on your Java version, one of the two setups below is required.

[NOTE]
====
The OpenSSL path is JVM-only. Native mode is not supported when relying on `smallrye-openssl` for PQC; use JDK 27+ for native image builds.
====

*Java < 27 (e.g., Java 21)*

* OpenSSL 3.5+ installed on the host machine
* `libapr-1` installed on the host machine (on UBI-based container images: `microdnf install -y apr`)
* `netty-tcnative-classes` and `smallrye-openssl` dependencies in `pom.xml`:

No additional dependencies required.

=== Step 1: Bootstrap the server

Create a basic Quarkus REST application using the Quarkus CLI or Maven.

[source,bash,role="primary asciidoc-tabs-target-sync-cli asciidoc-tabs-target-sync-maven"]
.CLI
----
quarkus create app org.acme:pqc-server \
    --extension='rest'
cd pqc-server
----

[source,bash,role="secondary asciidoc-tabs-target-sync-maven"]
.Maven
----
mvn io.quarkus.platform:quarkus-maven-plugin:3.40.1:create \
    -DprojectGroupId=org.acme \
    -DprojectArtifactId=pqc-server \
    -Dextensions='rest'
cd pqc-server
----

Before enabling PQC, the server must serve HTTPS. Generate a self-signed certificate and keystore:

[source,bash]
----
keytool -genkeypair -alias server -keyalg EC -keysize 256 \
  -storetype PKCS12 -keystore src/main/resources/server-keystore.p12 \
  -validity 3650 -storepass password \
  -dname "CN=localhost, OU=Test, O=Test, L=Test, ST=Test, C=US"
----

Add the following to `src/main/resources/application.properties`:

[source,properties]
----
quarkus.http.ssl-port=8443
quarkus.http.insecure-requests=disabled
quarkus.tls.key-store.p12.path=server-keystore.p12
quarkus.tls.key-store.p12.password=password
----

=== Step 2: Bootstrap the client

Create a second Quarkus application that will act as the REST client.

The scaffold generates a default `GreetingResource`. Delete it and create two new files under `src/main/java/org/acme/`.

`src/main/java/org/acme/GreetingClient.java` - a typed REST client interface that maps to the server endpoint:

[source,java]
----
package org.acme;

import org.eclipse.microprofile.rest.client.inject.RegisterRestClient;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

@RegisterRestClient(baseUri = "https://localhost:8443")

    @GET
    @Path("/hello")

----

`src/main/java/org/acme/ClientResource.java` - a REST endpoint that invokes the client and returns the result:

[source,java]
----
package org.acme;

import org.eclipse.microprofile.rest.client.inject.RestClient;
import jakarta.inject.Inject;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;
import jakarta.ws.rs.Produces;
import jakarta.ws.rs.core.MediaType;

@Path("/client")
public class ClientResource {
    @Inject
    @RestClient
    GreetingClient greetingClient;

    @GET
    @Produces(MediaType.TEXT_PLAIN)
    public String hello() {
        return greetingClient.hello();
    }
}
----

Since the server uses a self-signed certificate, export it and import it into the client's truststore so the TLS handshake can succeed:

[source,bash]
----
keytool -exportcert -alias server \
  -keystore ../pqc-server/src/main/resources/server-keystore.p12 \
  -storetype PKCS12 -storepass password -rfc \
  -file server.crt

keytool -importcert -alias server -file server.crt \
  -keystore src/main/resources/client-truststore.p12 \
  -storetype PKCS12 -storepass password -noprompt
----

Add the truststore configuration to `src/main/resources/application.properties`:

[source,properties]
----
quarkus.http.port=8081
quarkus.tls.client.trust-store.p12.path=client-truststore.p12
quarkus.tls.client.trust-store.p12.password=password
quarkus.rest-client."org.acme.GreetingClient".tls-configuration-name=client
----

`quarkus.tls.client.*` creates a *named* TLS configuration called `client` in the TLS registry. The `default` name is only registered when the application itself serves HTTPS. Since the client app has no TLS server, `default` doesn't exist. The REST client then references the named config via `tls-configuration-name`; without that line it sets up its own SSL context independently and ignores the registry entirely.

=== Step 3: Relaxed policy - baseline behavior

With both applications running in their default state, TLS is negotiated using classical key exchange groups. Explicitly set the enforcement policy on the server to `relaxed` to confirm the baseline:

[source,properties]
----
# pqc-server/src/main/resources/application.properties
quarkus.tls.pqc-enforcement-policy=relaxed
----

Start both applications and trigger the client:

[source,bash]
----
# Terminal 1 - server
cd pqc-server && ./mvnw quarkus:dev

# Terminal 2 - client
cd pqc-client && ./mvnw quarkus:dev

# Terminal 3 - test
curl http://localhost:8081/client
# → Hello from Quarkus REST
----

The connection succeeds as expected. Under `RELAXED`, the server imposes no constraint on the key exchange group negotiated with the client. Classical groups such as X25519 are accepted.

[NOTE]
====
On JDK 27+, X25519MLKEM768 is negotiated even without an enforcement policy. A server with no policy will still fall back to classical groups with a client that does not support PQC; `strict` turns that fallback into a hard failure at handshake time. Both `strict` and `client-negotiated` also fail at startup if no PQC-capable engine is available, surfacing misconfiguration early.
====

=== Step 4: Client-negotiated policy

`client-negotiated` is the recommended first step for a real deployment. The server advertises PQC groups and uses them with clients that support PQC, but falls back to classical key exchange with clients that do not. Existing peers are not disrupted.

Switch the server policy to `client-negotiated`:

[source,properties]
----
# pqc-server/src/main/resources/application.properties
quarkus.tls.pqc-enforcement-policy=client-negotiated
----

Dev mode picks up the change automatically via live reload. Trigger the client again:

[source,bash]
----
curl http://localhost:8081/client
# → Hello from Quarkus REST
----

The connection succeeds. A PQC-capable client negotiates X25519MLKEM768; a classical client negotiates a classical group and is still accepted.

=== Step 5: Strict policy - locking out classical peers

[WARNING]
====
`strict` rejects any peer that does not advertise PQC groups. On a *server*, this includes older clients, health checks, and load balancers that do not support PQC. On a *client*, this causes connection failures against any server that does not support PQC, including third-party APIs. Only use `strict` when all peers are known to support PQC.
====

Switch the server policy to `strict`:

[source,properties]
----
# pqc-server/src/main/resources/application.properties
quarkus.tls.pqc-enforcement-policy=strict
----

Trigger the client again:

[source,bash]
----
curl http://localhost:8081/client
# → HTTP 500 - javax.net.ssl.SSLHandshakeException: ...
----

The client fails to connect. The server now only accepts connections using PQC-compliant key exchange groups. The default Quarkus client does not advertise PQC groups, so the server rejects it.

Set the same policy on the client side:

[source,properties]
----
# pqc-client/src/main/resources/application.properties
quarkus.tls.client.pqc-enforcement-policy=strict
----

Trigger the client again:

[source,bash]
----
curl http://localhost:8081/client
# → Hello from Quarkus REST
----

The connection is restored. Both sides now advertise and negotiate X25519MLKEM768, and the TLS handshake completes using a quantum-resistant key exchange.

The enforcement policy selects key exchange groups and the SSL engine automatically. Two additional properties give fine-grained control when needed:

* `key-exchange-groups` pins the exact list of groups to advertise, for example `X25519MLKEM768,SecP256r1MLKEM768`. The three supported hybrid groups are `X25519MLKEM768`, `SecP256r1MLKEM768`, and `SecP384r1MLKEM1024`. The P-curve variants use NIST curves and matter for FIPS-constrained environments; `SecP384r1MLKEM1024` also aligns with CNSA 2.0, which mandates ML-KEM-1024.
* `ssl-engine` forces a specific engine (`jdkssl` or `openssl`) instead of letting the runtime select one.

== Enabling PQC in mTLS

In mutual TLS, both the client and the server authenticate each other using certificates, in addition to the standard server-only authentication. From a post-quantum perspective, mTLS introduces no additional complexity: the key exchange step is identical to regular TLS and X25519MLKEM768 is negotiated the same way regardless of whether mutual authentication is required.
The `pqc-enforcement-policy`, `key-exchange-groups`, and `ssl-engine` properties apply without modification.

The certificate-based mutual authentication step uses classical signature schemes (RSA or ECDSA) on both sides. As discussed in the introduction, forging a certificate signature requires a quantum computer operating in real time, which is a future concern rather than an immediate one.
Post-quantum signature schemes (such as ML-DSA) exist and are standardized, but migrating certificate authentication is a separate effort outside the scope of this article.

In practice, enabling PQC in a Quarkus mTLS setup requires only the same configuration changes described above, applied to both client and server.

== Scope

The `pqc-enforcement-policy`, `key-exchange-groups`, and `ssl-engine` properties, surfaced through `PqcEnforcementPolicy`, apply to connections managed through the Quarkus TLS registry. In a standard Quarkus application this covers:

* the HTTP server
* the HTTP client
* the REST client
* the Quarkus Mailer

Connections managed outside the TLS registry are not controlled by these properties. On JDK 27+, those connections still advertise X25519MLKEM768 automatically because the JDK SSL engine does so by default. On older JDKs, they negotiate classical groups regardless of any Quarkus configuration.

[NOTE]
====
If TLS terminates at an ingress controller or load balancer before reaching the Quarkus application, the enforcement policy has no effect on that hop. In that setup, PQC must be configured at the ingress level. This is a common deployment pattern and the Quarkus configuration described in this guide does not cover it.
====

== Conclusion

The rise of quantum computers threatens the security of TLS not only in a few years but also today: existing key exchange protocols such as X25519 are prone to harvest-now-decrypt-later attacks. Consequently, new Post-Quantum Cryptography (PQC) standards such as X25519MLKEM768 have been adopted to ensure that communications cannot be collected today and decrypted when a sufficiently capable quantum computer becomes available.

OpenSSL integrates these new schemes in its version 3.5, and in Java starting with version 27. The Java team is working to backport the integration to earlier versions: Java 25 by the 10th of October 2026, and Java 17/21 somewhere in the first half of 2027.

Due to the pressing nature of harvest-now-decrypt-later attacks, it was decided that Quarkus must integrate PQC in Java 21 before January 2027. To that end, `netty-tcnative` was used for Vert.x, the underlying engine of Quarkus, to leverage OpenSSL 3.5+ and benefit from PQC.

The API for setting PQC in both Vert.x and Quarkus is centered around three properties:

. `key-exchange-groups` is a user-supplied list of key exchange groups to use in TLS.
. `pqc-enforcement-policy` defines how the application will handle missing support for PQC: will the application crash or fall back on classical cryptography? It can take three values: `strict`, `client-negotiated`, `relaxed`.
. `ssl-engine` specifies the SSL engine the application should use: either JdkSSL or OpenSSL.

`pqc-enforcement-policy` is the easiest way to configure PQC:

* `strict`: uses only PQC schemes and crashes the application if none is available. The engine is selected automatically by the runtime.
* `client-negotiated`: the server must support PQC for clients asking for it, but can fall back on classical cryptography for clients without PQC support. Fails at startup if no PQC-capable engine is available.
* `relaxed`: no check is performed.

The initial contributions are available in Vert.x 4.5.28+ and Vert.x 5.1.0+, and were integrated in Quarkus 3.39.

Several areas remain open:

* *Clients outside the TLS registry*, such as Kafka consumers and producers and JDBC drivers, are not yet covered by the enforcement policy. On JDK 27+ those connections advertise X25519MLKEM768 by default; on older JDKs they negotiate classical groups regardless of any Quarkus configuration.
* *Native mode* support is pending a Mandrel release based on a PQC-capable JDK. Non-Linux platforms (macOS, Windows, IBM Power, IBM Z) also lack support today because `smallrye-openssl` does not ship native binaries for them.
* *Post-quantum signatures* (ML-DSA) for certificate authentication remain a separate effort, and one we intend to address as the ecosystem matures.
