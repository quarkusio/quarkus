== Entities

An entity is a Java class that represents data stored in a database. Typically, the class maps to a table, each entity
instance maps to a row, and its fields map to columns. Quarkus Data Hibernate works with entities defined using
Jakarta Persistence annotations.

=== Defining an entity

To map a Java class to a database table:

- Write a class.
- Annotate it with link:{jakarta-persistence-javadocs-url}/jakarta/persistence/entity[`@Entity`].
- Optionally, make it extend `ManagedEntity` or `RecordEntity` (see <<session-and-access-models,Session and access models>>).
- Make its fields `public`. <<entity-field-access,Getters and setters are not necessary thanks to bytecode enhancement>>.

[source,java]
----
import io.quarkus.data.hibernate.ManagedEntity;
import jakarta.persistence.Entity;

import java.time.LocalDate;

@Entity
public class Cat extends ManagedEntity {
    public String name;
    public LocalDate birth;
    public Breed breed;

    public enum Breed {
        CUTE, HAIRLESS;
    }
}
----

Instances of `ManagedEntity` are managed by Hibernate ORM. After an instance is persisted, changes to its fields are
automatically sent to the database without an explicit `update` instruction.

[[entity-field-access]]
=== Entity field access

Quarkus enhances entity bytecode at build time, so public fields can be accessed directly without writing getters and
setters. Missing getters and setters are generated, and public-field access is rewritten to invoke the corresponding
accessor methods. For example, reading `cat.name` invokes `getName()`, and assigning `cat.name` invokes `setName()`.
You can write these accessors yourself to add custom logic; callers can continue using the public field without changes.
Enhancement also tracks changes to managed entities. See
xref:hibernate-orm.adoc#automatic-build-time-enhancement[Automatic build time enhancement].
Public fields are a convenience, not a requirement: private fields with accessors and Jakarta Persistence property
access are also supported.

[[about-entity-identifiers]]
=== Entity identifiers

`ManagedEntity` and `RecordEntity` come with a default generated database identifier because they extend `WithId.AutoLong`, which
provides a generated database identifier of type `Long`.

You can choose to extend `WithId.AutoString` for a `String` identifier, `WithId.AutoUUID` for a `UUID` identifier,
or `WithId.AutoUUIDv7` for a time-sortable `UUID` identifier. The following table lists the identifier supertypes:

[cols="1,1,1"]
|===
|ID type|Supertype|Generation

|`Long`
|`WithId.AutoLong`
|`@GeneratedValue`

|`String`
|`WithId.AutoString`
|`@UuidGenerator`

|`UUID`
|`WithId.AutoUUID`
|`@UuidGenerator`

|`UUID`
|`WithId.AutoUUIDv7`
|`@UuidGenerator(style = UuidGenerator.Style.VERSION_7)`

|`Id`
|`WithId<Id>`
|Assigned by the application
|===

NOTE: `WithId<Id>` provides an inherited `@Id` field without an identifier generator. You must assign its value before
persisting the entity.

For example, extend `WithId.AutoUUIDv7` to use generated UUIDv7 identifiers:

[source,java]
----
import io.quarkus.data.hibernate.ManagedEntity;
import io.quarkus.data.hibernate.WithId;
import jakarta.persistence.Entity;

@Entity
public class CatWithUUID extends WithId.AutoUUIDv7 implements ManagedEntity.CustomId {
    public String name;
}
----

The entity inherits an `id` field of type `java.util.UUID`. When the entity is persisted, Hibernate automatically
generates a time-sortable version 7 UUID for this field. You do not need to declare or assign the identifier yourself.
Implementing `ManagedEntity.CustomId` also provides managed entity operations such as `persist()` and `delete()`.

You can also provide your own database identifier explicitly and implement the `ManagedEntity.CustomId` interface in
your entity, as well as use the `ManagedRepository.CustomId` interface for your repository, to specify the database
identifier type:

[source,java]
----
@Entity
public class CatWithId implements ManagedEntity.CustomId {
    @Id
    public String id;
    public String name;

    public interface Repo extends ManagedRepository.CustomId<CatWithId, String> {
        @Find
        CatWithId findByName(String name);
    }
}
----

WARNING: The custom identifier in this example has no generator, so you must set its value before persisting the entity.

You do not have to extend an identifier supertype if you define your own identifier. To combine a generated identifier
superclass with managed or record operations, implement the corresponding `CustomId` entity interface and extend the
corresponding `CustomId<Entity, Id>` repository interface; see <<entity-and-repository-type-matrix,the type matrix>>.

== Repositories

A Quarkus Data Hibernate repository is an interface containing annotated finder, query, or lifecycle methods.
The annotation processor generates its implementation. A repository may also declare unannotated `default` methods
for custom operations.

A repository does not need to extend another interface, but Quarkus Data provides a few repository supertypes worth
considering for convenience. The usual conventions are to nest the repository in its entity and extend
`ManagedRepository<Entity>` for managed entities, or `RecordRepository<Entity>` for record entities. These supertypes
provide ready-made persistence and query operations in addition to your declared methods.

.Managed entity and repository

[source,java]
----
@Entity
public class Cat extends ManagedEntity {
    public String name;
    public LocalDate birth;
    public Breed breed;

    public enum Breed {
        CUTE, HAIRLESS;
    }

    public interface Repo extends ManagedRepository<Cat> {
        @Find
        Cat findByName(String name);

        @Query("where breed = CUTE")
        List<Cat> findCute();

        @Query("delete from Cat where name = :name")
        long deleteByName(String name);

        @Query("delete from Cat where breed = HAIRLESS")
        long deleteHairless();
    }
}
----

.Record entity and repository
[source,java]
----
@Entity
public class CatRecord extends RecordEntity {
    public String name;

    public interface Repo extends RecordRepository<CatRecord> {
        @Find
        CatRecord findByName(String name);
    }
}
----

The examples use `jakarta.data.repository.Find` and `jakarta.data.repository.Query`.
For the behavioral differences between managed and record entities, see
<<session-and-access-models,Session and access models>>. For standalone repositories and entities without Quarkus Data
supertypes, see <<alternative-repository-definitions,Advanced usage>>.

=== Generated finder and query methods

You can use `@Find` methods to find single instances or collections of entities by using the parameters of the method
to build a query. The Hibernate documentation contains the complete
link:https://docs.hibernate.org/orm/{hibernate-orm-version-major-minor}/introduction/html_single/#generated-finder-methods[generated finder method reference].

.A few common examples
[source,java]
----
@Find
List<Cat> findAllCats(); <1>

@Find
long countAllCats(); <2>

@Find
Cat findCatByNameAndBreed(String name, Breed breed); <3>
----
<1> Finder methods may return collections of entities
<2> Or generate `COUNT` queries
<3> Or single entities, and any number of parameters which must all match the queried entities.

Alternatively, use Jakarta Data's `@Query` for entity queries or Jakarta Persistence's
`jakarta.persistence.query.NativeQuery` for native SQL. Jakarta Data's `@Query` supports JPQL and its portable
Jakarta Data Query Language subset (JDQL). Hibernate also accepts HQL extensions in `@Query`. The Hibernate documentation contains the complete
link:https://docs.hibernate.org/orm/{hibernate-orm-version-major-minor}/introduction/html_single/#generated-query-methods[generated query method reference].

.Examples of `@Query` and `@NativeQuery` usage
[source,java]
----
@Query("from Cat")
List<Cat> findAllCats(); <1>

@Query("select min(birth) from Cat")
LocalDate oldestCat(); <2>

@Query("where name = :name and breed = :breed")
Cat findCatByNameAndBreed(String name, Breed breed); <3>

@NativeQuery("select name from Cat where name = :name")
List<String> findNames(String name); <4>
----
<1> Query methods may return collections of entities
<2> Or projections of a single column, even multiple columns with `Object[]` and `List<Object[]>` types
<3> Queries can of course refer to method parameters.
<4> Native queries refer to database tables and columns instead of entity names and fields.

Generated finder and HQL query methods are type-checked at build time. They are validated for entity names, fields,
HQL syntax, and parameter names. Native SQL is validated by the database when the query is executed.

=== Obtaining and using a repository

Repositories are CDI beans and can be injected where you intend to use them:

[source,java]
----
@Inject
Cat.Repo repo;

@Transactional
public Cat findCat(String name) {
    return repo.findByName(name);
}
----

You can also access a nested repository by using a generated static method on the
link:https://docs.hibernate.org/orm/{hibernate-orm-version-major-minor}/introduction/html_single/#static-metamodel[generated metamodel]
of your entity:

[source,java]
----
Cat cat = Cat_.repo().findByName("Lucky");
----

All repositories defined as nested interfaces of an entity are available under their generated metamodel class through
accessor methods with the same name as the repository. This is equivalent to injecting the repository type and uses CDI
under the hood to look up the repository.

=== The `ManagedRepository` supertype

The `ManagedRepository` type provides most of the operations needed to work with an entity, such as `persist()`,
`delete()`, `isPersistent()`, and `listAll()`.

Here is an example of how it can be used:

[source,java]
----
@Inject
Cat.Repo repo;

@Transactional
public void repositoryOperations(Cat cat) {
    // entity operations
    repo.persist(cat);
    repo.delete(cat);
    boolean isPersistent = repo.isPersistent(cat);
    // operations on all entities
    long count = repo.count();
    long deleted = repo.deleteAll();
    List<Cat> allCats = repo.listAll();
    repo.streamAll().forEach(kitty -> kitty.name = kitty.name.toUpperCase());
    BlockingDataQuery<Cat> catQuery = repo.findAll();
    List<Cat> sortedCats = repo.findAll().sort(Sort.asc("name")).list();
    // operations on the Hibernate session
    repo.flush();
    Session session = repo.getSession();
    // ID-related operations
    boolean wasDeleted = repo.deleteById(cat.id);
    Cat foundCat = repo.findById(cat.id);
    Optional<Cat> optionalCat = repo.findByIdOptional(cat.id);
}
----

=== Dynamically built queries

When defining finder and query operations on a repository, queries are validated and generated at build time.
For dynamic filtering and sorting, prefer type-safe restrictions and ordering before using query strings.

==== Type-safe restrictions and ordering

Jakarta Data 1.1 provides `Restriction` parameters for finder and query methods. For example, add this method to
`Cat.Repo`:

[source,java]
----
import jakarta.data.Order;
import jakarta.data.restrict.Restriction;
import jakarta.data.repository.Find;

@Find
List<Cat> search(Restriction<Cat> restriction, Order<Cat> order);
----

The annotation processor generates two different metamodels for `Cat`:

- `_Cat`, with a leading underscore, is the Jakarta Data metamodel. Its typed attributes build restrictions and sort criteria.
- `Cat_`, with a trailing underscore, is the Jakarta Persistence metamodel. Its string attribute constants are used in the next subsection.

Both are generated in the same package as `Cat`; the examples below assume `org.acme`.
Use `_Cat` for type-safe restrictions and ordering:

[source,java]
----
import jakarta.data.restrict.Restrict;
import org.acme._Cat; // Automatically generated Jakarta Data metamodel (leading underscore)

@Inject
Cat.Repo repo;

@Transactional
public List<Cat> typeSafeQueries() {
    return repo.search(
            Restrict.all(_Cat.name.startsWith("Luck"), _Cat.breed.equalTo(Cat.Breed.CUTE)),
            Order.by(_Cat.name.asc(), _Cat.birth.desc()));
}
----

The attribute types determine which comparisons are available and which values they accept. Restrictions can be
combined conditionally to build a query from user-supplied search criteria. See the Hibernate documentation on
link:https://docs.hibernate.org/orm/{hibernate-orm-version-major-minor}/introduction/html_single/#restrictions-and-ordering[restrictions and ordering]
and the link:{jakarta-data-spec-url}[Jakarta Data specification] for the full APIs.

==== Queries using metamodel attribute constants

The query methods provided by `ManagedRepository` and `RecordRepository` can use attribute constants from the
generated Jakarta Persistence metamodel `Cat_`. These constants contain attribute names as strings; unlike the
typed attributes of `_Cat`, they do not make query parameters or expressions type-safe.

[source,java]
----
import org.acme.Cat_; // Automatically generated Jakarta Persistence metamodel (trailing underscore)

@Inject
Cat.Repo repo;

@Transactional
public void metamodelAttributeQueries() {
    // Find a cat by name
    Cat cat = repo.find(Cat_.NAME, "Lucky").singleResult();
    // All cute cats
    List<Cat> cuteCats = repo.list(Cat_.BREED, Cat.Breed.CUTE);
    // Cats with no known birth date
    repo.stream(Cat_.BIRTH + " is null").forEach(kitty -> System.err.println(kitty));
    // Get rid of non-cute cats
    long deleted = repo.delete(Cat_.BREED, Cat.Breed.HAIRLESS);
}
----

==== String-based queries

For queries that cannot be expressed with restrictions, use the query methods provided by `ManagedRepository` or
`RecordRepository`. These methods accept query strings, so they are not type-safe.

[source,java]
----
@Inject
Cat.Repo repo;

@Transactional
public void nonTypeSafeQueries() {
    // Count ugly cats with no name
    repo.count("breed = ?1 and name is null", Cat.Breed.HAIRLESS);
    // Make every cat cute
    repo.update("breed = CUTE");
    // Sort results using BlockingDataQuery
    List<Cat> sortedByName = repo.findAll().sort(Sort.asc("name")).list();
    List<Cat> sortedMatches = repo.find("breed = ?1", Cat.Breed.CUTE)
            .sort(Sort.desc("name"))
            .list();
}
----

Sorting is applied on the `BlockingDataQuery` returned by `find()` and `findAll()`, not on the shortcut `list()`,
`listAll()`, `stream()`, or `streamAll()` methods. For a single criterion, pass a `Sort` directly. Use `Order` only
when you need multiple criteria, or when receiving an `Order` from a REST endpoint:

[source,java]
----
List<Cat> byName = repo.findAll().sort(Sort.asc("name")).list();
List<Cat> byNameThenBirth = repo.findAll()
        .sort(Order.by(Sort.asc("name"), Sort.desc("birth")))
        .list();
----

[[session-and-access-models]]
== Session and access models

Quarkus Data Hibernate supports managed and stateless sessions with blocking and reactive APIs.

[[use-stateless-sessions]]
=== Record entities and stateless sessions

Subtypes of `ManagedEntity` are managed by Hibernate ORM, and changes to the entity are automatically sent to the
database without requiring an explicit `update` operation.

To make every update operation explicit, use a Hibernate ORM _stateless session_. Extend `RecordEntity` for the entity
and `RecordRepository` for its repository. Compared with a managed entity:

- Changes to entity fields must be explicitly pushed to the database by calling `update()` on the entity or repository.
- Call `insert()` instead of `persist()` to insert the entity.
- The session type is `StatelessSession` instead of `Session`.
- Accessing an unfetched lazy association does not trigger automatic loading. Fetch the associations you need as part
of a repository query, using a `join fetch` clause in `@Query`. Alternatively, fetch an association explicitly with
`repo.getSession().fetch(association)`. Managed blocking sessions can load lazy associations automatically while the
session is open.

Queries and the way you obtain entities remain the same. Stateless sessions can also use <<jakarta-data,Jakarta Data repositories>>.

[[lets-get-reactive]]
=== Reactive access

==== Reactive managed entities

For reactive access:

- The entity extends `ManagedEntity.Reactive`.
- The repository extends `ManagedRepository.Reactive`.
- Operations return `Uni<T>` instead of `T`, which is the standard Mutiny reactive type.
- Use `jakarta.transaction.Transactional` for transaction boundaries and compose operations as usual with Mutiny.

[source,java]
----
@Entity
public class ReactiveCat extends ManagedEntity.Reactive {
    public String name;

    public interface Repo extends ManagedRepository.Reactive<ReactiveCat> {
        @Find
        Uni<ReactiveCat> findByName(String name);
    }
}
----

With an injected `ReactiveCat.Repo repo`, operations are composed in a transaction:

[source,java]
----
@Transactional
public Uni<Void> renameCat(String name, String newName) {
    return repo.findByName(name)
            .invoke(cat -> cat.name = newName)
            .replaceWithVoid();
}
----

Changes to the managed entity are automatically flushed before the transaction commits. In reactive sessions, lazy associations
must be fetched explicitly, even for managed entities; see xref:hibernate-reactive.adoc[Hibernate Reactive].

[[reactive-and-stateless]]
==== Reactive record entities and stateless sessions

Use `RecordEntity.Reactive` and `RecordRepository.Reactive` for reactive stateless sessions. Changes must be explicitly
pushed by calling `update()`, and insertion uses `insert()` instead of `persist()`.

[source,java]
----
@Entity
public class ReactiveCatRecord extends RecordEntity.Reactive {
    public String name;

    public interface Repo extends RecordRepository.Reactive<ReactiveCatRecord> {
        @Find
        Uni<ReactiveCatRecord> findByName(String name);
    }
}
----

With an injected `ReactiveCatRecord.Repo repo`, explicitly update the modified entity:

[source,java]
----
@Transactional
public Uni<Void> renameCat(String name, String newName) {
    return repo.findByName(name)
            .chain(cat -> {
                cat.name = newName;
                return cat.update();
            });
}
----

The xref:quarkus-data-hibernate-getting-started.adoc#reactive[getting started tutorial] describes the
required dependencies and reactive datasource configuration. You can use any of the
xref:hibernate-reactive.adoc#hr-getting-started[supported reactive drivers].

== Startup code

For startup code, use `jakarta.transaction.Transactional` for both blocking and reactive operations. See the
xref:lifecycle.adoc#startup_annotation[application lifecycle guide] for information about `@Startup`.

.Blocking startup
[source,java]
----
import io.quarkus.runtime.Startup;
import jakarta.transaction.Transactional;

public class OnStart {
    @Startup
    @Transactional
    public void startupMethod() {
        Cat_.repo().deleteAll();
    }
}
----

.Reactive startup
[source,java]
----
import jakarta.transaction.Transactional;
import io.quarkus.runtime.Startup;
import io.smallrye.mutiny.Uni;

public class OnStartReactive {
    @Startup
    @Transactional
    public Uni<Void> startupMethod() {
        return ReactiveCat_.repo().deleteAll().replaceWithVoid();
    }
}
----

[[jakarta-data]]
== Jakarta Data

Quarkus Data Hibernate builds on the link:{jakarta-data-spec-url}[Jakarta Data] repository model and supports its
annotations directly. Entities can extend a variant of `ManagedEntity` or `RecordEntity`, or neither. The Jakarta Data
API is provided by the `quarkus-data-hibernate` extension, so no additional dependency is required.

For portable repository methods, use the Jakarta Data `@Find`, `@Query`, and `@Delete` annotations. Quarkus Data
Hibernate also supports the Jakarta Persistence-specific `@NativeQuery` annotation, which can be used alongside
Jakarta Data annotations in the same repository. The following example uses only Jakarta Data annotations:

[source,java]
----
@Entity
public class Cat {
    @Id
    @GeneratedValue
    public Long id;
    public String name;
    public LocalDate birth;
    public Breed breed;

    public enum Breed {
        CUTE, HAIRLESS;
    }

    public interface Repo extends RecordRepository<Cat> {
        @Find <1>
        Cat findByName(String name);

        @Query("where breed = CUTE") <2>
        List<Cat> findCute();

        @Delete <3>
        long deleteByName(String name);

        @Query("delete from Cat where breed = HAIRLESS") <4>
        long deleteHairless();
    }
}
----
<1> `@Find` defines a finder method from its parameters.
<2> `@Query` defines a query using the Jakarta Data Query Language.
<3> `@Delete` defines a finder-style delete method and can return the number of deleted entities.
<4> A delete operation can also be written explicitly with `@Query`.

Repositories are CDI beans and are also available through generated metamodel accessors such as `Cat_.repo()`.

Refer to the link:https://hibernate.org/repositories/[Hibernate Data Repositories] and
link:{jakarta-data-spec-url}[Jakarta Data] documentation for the complete repository API.

== REST integration

When your application uses both `quarkus-data-hibernate` and `quarkus-rest-jackson`, Quarkus automatically adds REST
support for common Jakarta Data parameter types. You can declare these types directly as REST endpoint parameters, and
they are populated from HTTP query parameters without manual parsing.

=== Supported parameter types

The following Jakarta Data types are automatically mapped from query parameters:

[cols="1,2,1,2"]
|===
|Jakarta Data type|Query parameters|Defaults|Example URL

|`PageRequest`
|`page`, `size`, `requestTotal`
|`page=1`, `size=10`, `requestTotal=true`
|`?page=2&size=25`

|`Sort<Cat>`
|`sort`
|`null`
|`?sort=name` (ascending) or `?sort=-name` (descending)

|`Order<Cat>`
|`sort` (repeating)
|empty `Order.by()`
|`?sort=name&sort=-salary`

|`Limit`
|`limit`, `startAt`, `endAt`
|`null` (no limit), `startAt=1`
|`?limit=10` or `?limit=10&startAt=51` or `?startAt=51&endAt=60`

|`Direction`
|`direction`
|`null`
|`?direction=ASC` or `?direction=desc`

|===

For `Sort` and `Order`, prefix the property name with `-` to indicate descending order.

When binding sort parameters from REST endpoints to `BlockingDataQuery`, prefer `Order<Cat>` over `Sort<Cat>`. A
missing `sort` query parameter yields `null` for `Sort<Cat>` but an empty `Order.by()` for `Order<Cat>`. If the
`Sort<Cat>` parameter is `null`, `.sort(null)` is a no-op. `Order` is preferred when multiple columns can be requested.

NOTE: Cursor-based pagination (`PageRequest.Mode.CURSOR_NEXT` and `CURSOR_PREVIOUS`) is not currently supported by this
REST integration. Only offset-based pagination is available through query parameters.

=== Page serialization

When a REST endpoint returns a `jakarta.data.page.Page`, it is serialized as a JSON object with pagination metadata,
rather than as a plain array:

[source,json]
----
{
  "content": [ ... ],
  "hasNext": true,
  "hasPrevious": false,
  "totalElements": 100,
  "totalPages": 34
}
----

The `totalElements` and `totalPages` fields are included only when the `PageRequest` was created with
`requestTotal=true`.

=== Example endpoint

Here is an example of a REST endpoint that uses `PageRequest` and `Order` to return a paginated, sorted
list of cats. Paging and sorting are configured on the `PanacheQuery` returned by `findAll()`:

[source,java]
----
import jakarta.data.Order;
import jakarta.data.page.PageRequest;
import jakarta.inject.Inject;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.Path;

import java.util.List;

@Path("cats")
public class CatResource {

    @Inject
    Cat.Repo repo;

    @GET
    public List<Cat> list(PageRequest pageRequest, Order<Cat> order) { // <1>
        return repo.findAll().pages().request(pageRequest).sort(order).list();
    }
}
----
<1> `PageRequest` is populated from `page`, `size`, and `requestTotal` query parameters.
`Order` is populated from repeating `sort` query parameters.

A client can then call:

[source]
----
GET /cats?page=1&size=20&sort=name&sort=-birth
----

This produces a `PageRequest.ofPage(1, 20, true)` and `Order.by(Sort.asc("name"), Sort.desc("birth"))`.

== Query languages

There are multiple technologies to express queries in Quarkus Data Hibernate. They are related languages rather than
separate query engines: each standard defines a different level of functionality or portability.

- The link:https://docs.hibernate.org/orm/{hibernate-orm-version-major-minor}/querylanguage/html_single/[Hibernate Query Language]
  (HQL) is Hibernate's full query language. Hibernate ORM accepts HQL in Jakarta Data's `@Query`, including features
  beyond the standard query languages.
- The link:{jakarta-persistence-spec-url}#a4665[Jakarta Persistence Query Language] (JPQL) is the standard query language
  defined by Jakarta Persistence and is a subset of HQL. A valid JPQL query is also a valid HQL query. This language is
  evolving into the standalone link:https://jakarta.ee/specifications/query/1.0/[Jakarta Query specification].
- The link:{jakarta-data-spec-url}#_jakarta_data_query_language[Jakarta Data Query Language] (JDQL) is the portable
  subset of JPQL used by Jakarta Data's `@Query` annotation. Restrict queries to JDQL when the repository should remain
  independent of Hibernate-specific query features.
- Panache Query Language adds concise forms for common HQL queries. It is accepted by query methods such as `find()`,
  `list()`, `update()`, and `delete()` on `ManagedRepository` and `RecordRepository`, and is expanded to HQL before
  execution.

=== Panache Query Language

Most HQL select queries have the form `from EntityName [where ...] [order by ...]`, with optional elements at the end.

If a select query does not start with `from`, `select`, or `with`, the following additional forms are supported:

- `order by ...` expands to `from EntityName order by ...`.
- `<singleAttribute>` with a single parameter expands to `from EntityName where <singleAttribute> = ?`.
- `where <query>` expands to `from EntityName where <query>`.
- `<query>` expands to `from EntityName where <query>`.

If an update query does not start with `update`, the following additional forms are supported:

- `from EntityName ...` expands to `update EntityName ...`.
- `set? <singleAttribute>` with a single parameter expands to `update EntityName set <singleAttribute> = ?`.
- `set? <update-query>` expands to `update EntityName set <update-query>`.

If a delete query does not start with `delete`, the following additional forms are supported:

- `from EntityName ...` expands to `delete from EntityName ...`.
- `<singleAttribute>` with a single parameter expands to `delete from EntityName where <singleAttribute> = ?`.
- `<query>` expands to `delete from EntityName where <query>`.

== Repository security

Quarkus Security provides initial support for securing repositories with security annotations. Security annotations can
be placed on methods directly declared by a repository.

[source,java]
----
@PermissionsAllowed("cat:list")
@PermissionsAllowed("cat:read")
@Find
List<Cat> findByName(String name);
----

You can also place a security annotation on the repository interface:

[source,java]
----
@RolesAllowed("admin")
public interface SecuredCatRepo extends ManagedRepository<Cat> {
    @Find
    List<Cat> findByName(String name);
}
----

[WARNING]
====
Only methods directly declared on an annotated repository interface are secured. Methods inherited from
`ManagedRepository`, such as `findById`, `persist`, or `deleteAll`, are not secured because type-level annotations only
affect the type they annotate.

If you need security in the repository layer, consider <<alternative-repository-definitions,plain repository classes>> that do not extend Quarkus Data ones, or roll out your own repository super interfaces, adding security annotations wherever relevant for your security model.
====

Generic interface methods using type variables or wildcards cannot currently be secured reliably with standard security
annotations. Apply the security annotation to the calling method, such as a REST endpoint, or redeclare the repository
method with a concrete type.

See the xref:security-authorize-web-endpoints-reference.adoc[authorization of web endpoints reference] for information
about Quarkus Security annotations.

== Advanced usage

[[alternative-repository-definitions]]
=== Standalone repositories and entities without supertypes

Neither an entity nor its repository has to extend a Quarkus Data supertype. This is useful when an entity already
extends an application-specific superclass, or when the repository should expose only explicitly declared operations:

[source,java]
----
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.Id;

@Entity
public class PlainCat {
    @Id
    @GeneratedValue
    public Long id;
    public String name;
}
----

A repository can also be a top-level interface. Annotate standalone repositories with `jakarta.data.repository.Repository`:

[source,java]
----
import jakarta.data.repository.Find;
import jakarta.data.repository.Repository;

@Repository
public interface PlainCatRepository {
    @Find
    PlainCat findByName(String name);
}
----

The generated repository remains a CDI bean and can be injected as `PlainCatRepository`. It only exposes the declared
finder, because it does not inherit persistence or query operations. A standalone repository can also extend
`ManagedRepository<PlainCat>` or `RecordRepository<PlainCat>` to inherit those operations. Conversely, a nested repository
can omit the supertype; nesting and inheritance are independent choices.

=== Switching between managed and record models

You can access an entity using any supported session model, regardless of the entity supertype. Pick the supertype that
represents the majority of your use cases and use the following accessors for alternative operations:

[cols="1,1,1"]
|===
|Session type|Entity accessor|Equivalent entity type

|`Session`
|`.managedBlocking()`
|`ManagedEntity`

|`StatelessSession`
|`.statelessBlocking()`
|`RecordEntity`

|`Mutiny.Session`
|`.managedReactive()`
|`ManagedEntity.Reactive`

|`Mutiny.StatelessSession`
|`.statelessReactive()`
|`RecordEntity.Reactive`

|===

For repository operations, obtain alternative repositories from the generated metamodel accessors, or inject them with
`@Inject`:

[cols="1,1,1"]
|===
|Session type|Metamodel accessor|Repository type

|`Session`
|`Cat_.managedBlocking()`
|`ManagedRepository<Cat>`

|`StatelessSession`
|`Cat_.statelessBlocking()`
|`RecordRepository<Cat>`

|`Mutiny.Session`
|`Cat_.managedReactive()`
|`ManagedRepository.Reactive<Cat>`

|`Mutiny.StatelessSession`
|`Cat_.statelessReactive()`
|`RecordRepository.Reactive<Cat>`

|===

You can also define any number of repositories for custom operations within an entity. All nested repositories are
available through generated metamodel accessors, such as `Cat_.repo()` and `Cat_.theOtherRepo()`.
