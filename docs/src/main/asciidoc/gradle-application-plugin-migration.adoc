[id="gradle-application-plugin-migration"]
= Migrate to the io.quarkus.application Gradle plugin
include::_attributes.adoc[]
:diataxis-type: howto
:categories: tooling, native
:extension-status: preview
:summary: Migrate a Quarkus 3 Gradle application from io.quarkus to the preview Quarkus 4 application plugin.
:topics: gradle,tooling,migration

The preview `io.quarkus.application` Gradle plugin replaces the application-build responsibilities of the legacy `io.quarkus` plugin with explicit named builds and Gradle-native ownership boundaries.
This guide describes two migration shapes:

* a _direct migration_, which removes `io.quarkus` and moves its responsibilities in one change; and
* a _legacy-first staged migration_, which temporarily applies both plugins, moves responsibilities in stages, and removes `io.quarkus` when those stages are complete.

The two shapes are described neutrally.
They converge on the same standalone-only build when a staged migration is completed, but have different ownership and compatibility boundaries while both plugins are applied.

This guide starts from an existing Quarkus 3 application that uses the xref:gradle-tooling.adoc[`io.quarkus` plugin].
For the complete target DSL and task reference, see xref:gradle-application-plugin.adoc[The `io.quarkus.application` Gradle plugin].

[[gradle-application-plugin-migration-prerequisites]]
== Update the target prerequisites

The Quarkus 4 target requires Java 21 and Gradle 9.6 or later.
Update the JDK that runs Gradle and the Gradle wrapper before diagnosing plugin-migration failures.

The following command updates the wrapper to the version used to verify this documentation:

[source,shell,subs=attributes+]
----
./gradlew wrapper --gradle-version {gradle-version}
----

Commit the generated wrapper files with the migration.
Update `quarkusPluginVersion` and `quarkusPlatformVersion` wherever the build declares them, commonly in `gradle.properties`, to the selected Quarkus 4 release.
If plugin or platform versions are declared inline or through a version catalog, update those declarations instead.
The plugin IDs used during migration must resolve from the same Quarkus 4 distribution; coexistence does not combine a Quarkus 3 legacy plugin with a Quarkus 4 standalone plugin.
These target requirements do not describe the Java and Gradle versions supported by every Quarkus 3 release.

[[gradle-application-plugin-migration-compare]]
== Compare the migration shapes

[cols="2,3,3"]
|===
|Concern |Direct migration |Legacy-first staged migration

|Applied plugins
|Only `io.quarkus.application`
|`io.quarkus` first, then `io.quarkus.application`

|Legacy tasks
|Removed with `io.quarkus`
|Remain available until `io.quarkus` is removed

|Standalone named tasks and package variants
|Available
|Available within the coexistence restrictions described in <<gradle-application-plugin-migration-staged>>

|Gradle `Test` ownership
|Standalone selection and JVM Test Suite model
|Legacy instrumentation

|Tooling-model ownership
|Standalone provider and sidecar
|Legacy provider

|Code generation
|Standalone task family and output roots
|Both task families can feed compilation; separate output roots do not prevent duplicate generated classes

|`quarkusDev` dependency configuration
|Created by the standalone plugin
|The existing legacy-owned configuration is reused

|Standalone continuous testing
|Available
|Rejected while the legacy plugin owns testing; standalone dev mode remains available with continuous testing disabled

|Named native tests
|Generated for each named native executable
|Suppressed; use the legacy native-test surface until the legacy plugin is removed

|Package-backed JVM integration tests
|Available for named JAR and native-executable builds
|May target a standalone named JAR; a standalone native-executable target is rejected

|Configuration Cache and Isolated Projects
|Finite standalone graphs are designed for both
|Standalone guarantees do not extend to legacy configuration or tasks; compatibility remains specific to the selected graph and build logic
|===

Only legacy-first plugin application is supported during coexistence.
Applying `io.quarkus.application` first and `io.quarkus` afterward is rejected.
Coexistence is a migration-only contract, not a combined long-term feature mode or a statement that the legacy plugin is deprecated on a particular schedule.

[[gradle-application-plugin-migration-inventory]]
== Inventory the existing build

Before changing the plugin declaration, identify which legacy responsibilities the build uses:

* `io.quarkus`, the `quarkus` extension, and any convention plugins that configure them;
* `quarkusBuild`, `quarkusRun`, `assemble`, package type, final name, output path, manifest, native arguments, or ignored JAR entries;
* `quarkusDev`, `quarkusTest`, `quarkusRemoteDev`, and development-only dependencies declared in the `quarkusDev` configuration;
* standard or custom finite `Test` tasks, the `integrationTest` source set, `quarkusIntTest`, `native-test`, `testNative`, or `buildNative`;
* code-generation providers and inputs, effective-configuration diagnostics, offline preparation, and application-model consumers;
* project properties, system properties, environment variables, and `cachingRelevantProperties` patterns that supply build configuration;
* image build or push, deployment, AOT/startup-archive work, and external prerequisites for those operations;
* package consumers and publications that locate the legacy output directly; and
* extension discovery or mutation, project information, and project-update tasks.

Also search convention plugins for live-project helpers exposed by the legacy `quarkus` extension, such as application-model, resolver, source-output, or application-JAR accessors.
The standalone plugin does not expose those helpers as a compatibility API.

The build logs a migration-mode warning describing the required order and ownership split.
During this stage:

* legacy task names and the `quarkus` extension remain available;
* standalone named builds, applicable run tasks, variants, images, deployments, offline preparation, and diagnostics remain available under their standalone names;
* the legacy plugin owns finite test instrumentation and the Tooling API application-model provider;
* the standalone plugin reuses the existing legacy-owned `quarkusDev` dependency configuration without changing its roles;
* a package-backed JVM integration suite can consume a standalone named JAR, with legacy supplying test instrumentation;
* standalone generated native-test suites are suppressed, and targeting a standalone native executable from a user-owned integration suite is rejected;
* `quarkusApplicationContinuousTest` and `quarkusApplicationDev` with continuous testing enabled are rejected; `quarkusApplicationDev` remains available when continuous testing is disabled; and
* both code-generation families can feed compilation from different output roots.

The plugins do not arbitrate duplicate generated classes.
If both generators produce the same fully qualified source, separate output directories do not make the resulting compilation valid.

The legacy plugin adds its global `quarkusBuild` task to `assemble`.
Each standalone named build still uses its own `participatesInAssemble` flag.
Consequently, opting a standalone build into `assemble` during coexistence intentionally selects both the legacy package and that standalone package.

Development-only dependencies stay in the same public `quarkusDev` configuration shown in the coexistence example.
This name is a dependency configuration, not the legacy task of the same name.
The standalone dev and continuous-test runtime classpaths extend from the legacy-owned configuration during coexistence.

== Map legacy outcomes to standalone outcomes

The following tables cover the user-facing outcomes of the legacy application plugin.

=== Build, lifecycle, output, and development dependencies

[cols="2,3,3"]
|===
|Legacy surface |Standalone action |Difference to account for

|`io.quarkus`
|Apply `io.quarkus.application`
|No implicit package output; coexistence supports legacy-first order only.

|`quarkus` extension
|Use `quarkusApplication` concern blocks and named builds
|Global concerns are split by responsibility and output.

|`quarkusBuild`
|Declare a build and run `quarkus<Name>Build`
|There is no universal package-task alias.

|Automatic `assemble -> quarkusBuild`
|Set `participatesInAssemble=true` on each selected build
|Participation is per build and opt-in.

|`quarkusRun`
|Run a JAR build's `quarkus<Name>Run`
|The task consumes an explicit named package receipt.

|`quarkusDev` dependency configuration
|Keep declaring development-only dependencies in `quarkusDev`
|Standalone creates it alone and reuses the legacy owner during coexistence.

|Global manifest DSL
|Configure `manifest.attributes` and named `sections` on each named JAR build
|The string-map model is per output, is not Gradle's `Manifest`, and is absent from native builds.

|Global final name and output
|Configure each build's `outputDirectory`, `outputName`, archive components, and runner suffix
|The default is `build/quarkus-builds/<name>/package`; `project.version=unspecified` requires an explicit version or output name.

|Ambient build configuration and `cachingRelevantProperties`
|Use root/concern/build properties and `configInputs` prefixes or exact names
|Selectors are finite, and there is no general regex conversion. Temporary ambient capture disables safe reuse for affected tasks.
|===

[cols="2,3,3"]
|===
|Legacy surface |Standalone action |Difference to account for

|`quarkusDev` task

|`quarkusRemoteDev`

[[gradle-application-plugin-migration-dsl-details]]
== Account for detailed DSL changes

=== Native arguments and ignored JAR entries

The legacy `quarkusBuild.nativeArgs` helper converted camel-case names to hyphenated `quarkus.native.*` keys.
The standalone named-native-build map uses complete Quarkus configuration keys.
For example, the source-backed direct-migration example changes the legacy container-build entry to the complete `quarkus.native.container-build` key in the selected `native` output's `nativeArguments` map.

The standalone task family does not provide the legacy repeatable `quarkusBuild --ignored-entry` option.
For a selected uber-JAR output, put the comma-delimited entry names in that build's `quarkus.package.jar.user-configured-ignored-entries` build property.

=== Output consumers and publications

Each named JAR publishes a complete-package directory variant and a launcher-JAR variant.
A fast-, AOT-, legacy-, or mutable-JAR launcher can require sibling files, so consuming only that launcher does not create a portable distribution.
An uber JAR is independently runnable.

Consuming either variant as a task input carries the producing named-build task dependency, including when the consumer is a different project or an included build in the same Gradle build tree.
No additional `dependsOn` is needed for that task input.
Resolving a configuration eagerly or from arbitrary configuration-time logic does not itself execute the producing task.

Use ordinary Gradle `Zip`, Zip64-enabled `Zip`, or `Tar` tasks when a package directory needs an archive, and attach the chosen archive to a Maven publication when required.
The standalone plugin does not select an archive format.
See xref:gradle-application-plugin.adoc#gradle-application-plugin-package-variants[Consume, archive, and publish packages] for configuration-name and attribute-based selection examples.

=== Legacy extension helpers and cache controls

There is no direct standalone equivalent for legacy extension helpers that expose a live application model, resolver, source outputs, or application JAR/classes.
Move convention-plugin consumers to declared model tasks, Gradle Tooling API models, package variants, task outputs, or providers according to the value they actually consume.

The legacy `cleanupBuildOutput` switch has no direct equivalent because named builds own separate output directories.
The legacy `cacheLargeArtifacts` switch also has no direct equivalent: finite standalone tasks support up-to-date checks but are not currently reusable through Gradle's build cache.
Up-to-date checks, Configuration Cache reuse, and the build cache are separate mechanisms.

[[gradle-application-plugin-migration-validation]]
== Validate the migrated build

For a direct migration or the final standalone-only state, run the finite graph twice with Configuration Cache and Isolated Projects:

[source,shell]
----
./gradlew assemble test --configuration-cache -Dorg.gradle.unsafe.isolated-projects=true
./gradlew assemble test --configuration-cache -Dorg.gradle.unsafe.isolated-projects=true
----

The second invocation should reuse the configuration cache.
Tasks with unchanged declared inputs and outputs can be up to date.
This does not prove that their outputs are reusable through Gradle's build cache.

During coexistence, apply those flags only to a selected finite graph after checking the legacy build logic used by that graph.
Applying the standalone plugin does not make legacy configuration, tasks, or user build logic compatible with Configuration Cache or Isolated Projects.

Launch the standalone long-lived task families with Gradle continuous build and without Configuration Cache:

[source,shell]
----
./gradlew quarkusApplicationDev --continuous --no-configuration-cache
./gradlew quarkusApplicationContinuousTest --continuous --no-configuration-cache
./gradlew quarkusApplicationRemoteDev --continuous --no-configuration-cache
----

Native builds and tests require a supported native-image toolchain or container environment.
Image, registry, and deployment checks require the selected extension/provider, daemon or service, credentials, and target access.
Startup archive and optimized-image checks additionally depend on the selected archive technology, JVM, and training environment.
Registration or a Gradle dry run proves only the task graph, not these external operations.

[[gradle-application-plugin-migration-troubleshooting]]
== Troubleshoot migration failures

[cols="2,4"]
|===
|Symptom |Check

|The legacy plugin fails when both plugins are applied
|Apply `io.quarkus` first and `io.quarkus.application` second. The reverse order is unsupported.

|No standalone package task exists
|Declare a named build. The standalone plugin creates no package output implicitly.

|A legacy task name is missing after direct migration
|Use the named task or concern-specific standalone task; the plugin does not register general compatibility aliases.

|`assemble` does not build a named output
|Set `participatesInAssemble=true` on that named build.

|`assemble` builds two packages during coexistence
|The legacy package always participates, and the standalone named build was opted in. Run the named standalone task directly or change its lifecycle opt-in when only one package is intended.

|A package fails because the version is `unspecified`
|Set `project.version`, `archiveVersion`, or an explicit `outputName`.

|Standalone continuous testing fails during coexistence
|The legacy plugin owns testing. Use the legacy continuous-test surface until removing it, or run standalone dev mode with continuous testing disabled.

|A named native-test task is missing during coexistence
|Legacy owns native testing in this mode. Named standalone native-test suites appear after the legacy plugin is removed.

|A named native integration suite is rejected during coexistence
|Target a standalone JAR for package-backed JVM integration testing, use the legacy native-test surface, or complete removal of the legacy plugin.

|Compilation reports duplicate generated classes during coexistence
|Both code-generation task families can feed compilation. Identify the duplicate provider/output and complete the relevant ownership transition; separate generated directories do not deduplicate classes.

|A configuration value no longer reaches a finite task
|Declare its exact name or prefix under `configInputs`, or move a build-owned value into `quarkusBuildProperties`. Use ambient capture only as a temporary migration bridge.

|A custom task or provider prevents Configuration Cache or Isolated Projects reuse
|Use provider-backed paths such as `layout.buildDirectory` and `gradle.settingsDirectory`; do not capture `project`, `rootProject`, or another project's live model in task actions or providers.

|Dev, continuous test, or remote dev rejects the invocation
|Add Gradle's `--continuous --no-configuration-cache` options.

|A copied layout launcher does not start
|Consume or archive the complete package-directory variant. Only an uber-JAR launcher is portable by itself.

|Native, image, push, deployment, or startup-archive work cannot execute
|Check the toolchain, provider extension, container/registry/platform access, credentials, JVM, and operation-specific prerequisites.
