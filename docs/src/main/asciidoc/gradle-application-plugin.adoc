= The io.quarkus.application Gradle plugin
include::_attributes.adoc[]
:diataxis-type: reference
:categories: tooling, native
:extension-status: preview
:summary: Build, test, run, and publish multiple Quarkus application outputs with the configuration-cache-compatible Gradle plugin.
:topics: gradle,tooling

The preview `io.quarkus.application` Gradle plugin is designed for Gradle's configuration cache and Isolated Projects.
It lets one project declare several independently configured application packages or native executables and gives each one its own build, test, run, image, deployment, and publication integration where applicable.
This avoids changing one project-wide package type when different consumers need different application forms.
See <<gradle-application-plugin-gradle-model,How the plugin works with Gradle's performance features>> for the Gradle concepts behind this design.

include::{includes}/extension-status.adoc[]

This plugin is different from the `io.quarkus` plugin used by currently generated projects.
Use this page for `io.quarkus.application`.
See xref:gradle-tooling.adoc[Quarkus and Gradle] for `io.quarkus`.
For direct migration and temporary legacy-first coexistence procedures, see xref:gradle-application-plugin-migration.adoc[Migrate to the `io.quarkus.application` Gradle plugin].

The plugin does not choose an application package for you.
Declaring a build registers its task family lazily, but does not run the build or add it to `assemble`.

[[gradle-application-plugin-prerequisites]]
== Prerequisites and plugin application

Quarkus 4 requires Java 21.
The Gradle plugins require Gradle 9.6 or later.
The repository wrapper, and the version used to verify this guide, is Gradle {gradle-version}.

Apply version {quarkus-version} of the plugin to the application project.
The plugin also applies Gradle's Java plugin.

[[gradle-application-plugin-named-builds]]
== Define named application builds

Each _named build_ describes one application output: its package type, output location and name, manifest, image settings, deployments, and other output-specific choices.
Names let several outputs coexist without a mutable global package setting and provide stable task and configuration names that other projects and automation can select.
For example, the same application can expose a fast JAR for a server distribution, an uber JAR for a command-line download, and a native executable for a container image.

Register named builds in `quarkusApplication.builds`.

A build name must:

* start with a letter;
* contain only letters, digits, hyphens, or underscores;
* not contain an empty segment, such as two adjacent separators; and
* derive a task-name segment that is unique, ignoring case, among the named builds.

Hyphens and underscores start a new capitalized task-name segment.
For example, `production-linux` becomes `ProductionLinux`.
Configuration fails if a derived name collides with another generated or existing task.

[[gradle-application-plugin-build-run]]
== Build and run named outputs

For a build named `production`, run:

[source,shell]
----
./gradlew quarkusProductionBuild
----

JAR builds also register:

[source,shell]
----
./gradlew quarkusProductionRun
----

The run task starts the package in the foreground and always executes.
It accepts `--jvm-args` and `--quarkus-args`.
Its working directory defaults to the project directory, and its optional run target uses the `quarkus.run.target` system property.
Run tasks are not configuration-cache compatible or build-cacheable because they own a foreground process.

The common generated task prefix is `quarkus<NameSegment>`.
See <<gradle-application-plugin-task-reference,the task reference>> for the complete suffix table.

[[gradle-application-plugin-package-output]]
== Configure package output

The default output directory for a build named `production` is:

[source,text]
----
build/quarkus-builds/production/package
----

The default `outputName` combines:

1. `archiveBaseName`, which defaults to `project.name`;
2. `archiveBaseNameSuffix`, which defaults to an empty string; and
3. `archiveVersion`, which defaults to `project.version` and is prefixed with `-` when non-empty.

If `project.version` is `unspecified`, configure `project.version`, `archiveVersion`, or `outputName`.
Setting `outputName` explicitly bypasses assembly of the three archive-name components.
Legacy-JAR, uber-JAR, native-executable, and native-sources outputs additionally default to `archiveRunnerSuffix="-runner"` and `archiveAddRunnerSuffix=true`.

The root `packageOutputTimestamp` convention is `1970-01-02T00:00:00Z`, which makes generated package-entry timestamps deterministic.
Call `unsetConvention()` on the property when timestamps must not be normalized.
An explicit `quarkus.package.output-timestamp` configuration value has normal Quarkus configuration precedence over the convention.

JAR builds expose a typed, per-output manifest model.
It contains a main attributes map and named sections, each with its own attributes map.
It is not Gradle's `org.gradle.api.java.archives.Manifest`: it has no `from` or merge API, and all keys and values are strings.

[[gradle-application-plugin-package-variants]]
== Consume, archive, and publish packages

Every named JAR build publishes two outgoing configurations:

Use `quarkus<Name>PackageElements` when the consumer needs a distributable application.
Its single directory artifact represents the complete package, including the files next to a fast-, AOT-, legacy-, or mutable-JAR launcher that are required at runtime.
Copy, archive, or publish that directory as one unit.

Use `quarkus<Name>LauncherJarElements` only when the consumer deliberately needs the primary JAR at its existing producer-owned location, for example to launch it from an integration test elsewhere in the same Gradle build tree.
The consumer can be another project with its own build script or a project in an included build; it need not be the producing project.
Resolving this variant does not copy required sibling files, so the launcher of a layout-based package is not a portable distribution by itself.

[cols="2,2,3"]
|===
|Configuration |Artifact |Contract

|`quarkus<Name>PackageElements`
|One directory
|The complete relocatable package tree.

|`quarkus<Name>LauncherJarElements`
|One JAR at its producer-owned location
|The primary launcher only. Fast-, AOT-, legacy-, and mutable-JAR launchers can require sibling package files.
An uber JAR is independently runnable.
|===

The variants intentionally do not publish Java usage, target-JVM, or bundling attributes.
They use the following public attributes:

[cols="2,3"]
|===
|Attribute |Value

|Category
|`quarkus-application-package` or `quarkus-application-launcher`

|Library elements
|`quarkus-application-package-directory` or `quarkus-application-launcher-jar`

|Artifact type
|`directory` or `jar`

|`io.quarkus.application.build-name`
|The original named-build name

|`io.quarkus.application.build-type`
|`fast-jar`, `aot-jar`, `legacy-jar`, `mutable-jar`, or `uber-jar`
|===

Use the producer's configuration name directly in a tightly coupled build, as the following example does.
This selects that exact outgoing configuration; the consumer does not also need matching attributes.
It remains compatible with configuration cache and Isolated Projects: the project dependency selects a published configuration by name without reading the producer project's model, and the consumer treats its own resolvable configuration as a lazy file collection.
The trade-off is coupling to the producer's generated configuration name.
To remain decoupled from the producer's configuration name, use ordinary variant-aware project or included-build dependency selection and set all five attributes in the table on the resolvable consumer configuration, as shown below.

Resolving either configuration as a task input automatically adds the producing `quarkus<Name>Build` task to the task graph.
You do not need an additional `dependsOn` for the package build.

[[gradle-application-plugin-dev-mode]]
== Develop with Gradle continuous build

Run dev mode with:

[source,shell]
----
./gradlew quarkusApplicationDev --continuous --no-configuration-cache
----

The `--continuous` option is mandatory.
It tells Gradle to watch the task's declared source, resource, generated-source, and dependency inputs and rerun the task graph after a change.
The plugin retains the Quarkus process between those executions and sends it each successful set of new build outputs.
Without Gradle continuous build there can be no later iteration, so the task rejects the invocation instead of starting a session that cannot receive changes.
Pass `--no-configuration-cache` explicitly because these long-lived plugin tasks deliberately opt out of configuration-cache reuse.
The flag also avoids the current Gradle 9.6 Kotlin DSL continuous-build failures tracked in
link:https://github.com/gradle/gradle/issues/34013[Gradle issue 34013] and
link:https://github.com/gradle/gradle/issues/38482[Gradle issue 38482].

Gradle owns compilation, resource processing, code generation, and continuous-build cancellation.
The long-lived Quarkus process receives successful output changes.
Compilation failures are reported to the running application without replacing the last successful baseline; a later successful iteration clears the failure.
When a precise change set is too large, the plugin sends a complete output rebaseline.
If live reload is disabled, successful changes are retained and replayed automatically after it is re-enabled.

When continuous testing is enabled, the task logs a browser Dev UI URL after Quarkus reports its main HTTP listen address.
For example:

[source,text]
----
Continuous Testing Dev UI: http://localhost:8080/q/dev-ui
----

The current log parser deliberately ignores the management listener.
If the Dev UI is exposed on a separately configured management interface, use its actual management address instead of the logged main-interface URL.
Browser-based continuous-testing controls remain available through Dev UI.
Console stdin controls are not inherited because Gradle owns stdin.
For a broader comparison of Quarkus development modes, see
xref:dev-mode-differences.adoc[Differences between Quarkus dev mode and a production application].

[[gradle-application-plugin-continuous-testing]]
== Run dedicated continuous testing

Run the default test suite continuously with:

[source,shell]
----
./gradlew quarkusApplicationContinuousTest --continuous --no-configuration-cache
----

The dedicated task fixes continuous testing to `true` and prevents the ordinary `test` task from running concurrently when the dedicated task is selected explicitly.
It runs without dev mode, so Dev UI and its browser controls are not available.
It accepts the dev/continuous-test command-line options in <<gradle-application-plugin-option-reference,the option table>>, except that continuous testing cannot be disabled.
Run `./gradlew help --task quarkusApplicationContinuousTest` to inspect the options supplied by the plugin version in the build.
For continuous-testing behavior and the controls available while using dev mode, see xref:continuous-testing.adoc[Continuous Testing].

Dev and continuous-test tasks are intentionally not configuration-cache compatible or build-cacheable.
With `--no-configuration-cache`, Gradle does not attempt to store or reuse a configuration-cache entry during the continuous session.
Cancellation stops the retained Quarkus process and releases the output tree.

Start a named mutable-JAR output as the remote server side:

[source,shell]
----
./gradlew quarkusRemoteRun \
    --enable-remote-dev \
    --live-reload-password=change-me
----

Then start the local synchronization loop:

[source,shell]
----
./gradlew quarkusApplicationRemoteDev \
    --continuous \
    --no-configuration-cache \
    --live-reload-url=https://remote.example.test \
    --live-reload-password=change-me
----

The URL and password task options override `quarkus.live-reload.url` and `quarkus.live-reload.password` for that invocation.
The password is transient task state and is not persisted by the plugin, but command lines and build logs still require normal credential-handling care.
If the remote application exposes management endpoints separately, use the live-reload endpoint on the interface where it is actually exposed.

[TIP]
====
In Bash, when `HISTCONTROL` contains `ignorespace` or `ignoreboth`, prefixing a command with a space keeps it out of the shell history.
Verify your shell configuration before relying on this behavior; other shells differ.
This only reduces shell-history exposure and does not hide arguments from process listings or logs.
====

The session reconnects automatically when the server reports a stale session, using a fresh complete package snapshot; no extra source edit is required.
Files that change after the local snapshot are rejected instead of uploading different bytes.

[WARNING]
====
Remote development is for development environments.
Do not expose its live-reload endpoint as a production application-management interface.
====

[[gradle-application-plugin-offline]]
== Prepare dependencies for offline work

Run:

[source,shell]
----
./gradlew quarkusApplicationPrepareOffline

[[gradle-application-plugin-images-deployments]]
== Build images and deploy

Every named build registers `quarkus<Name>ImageBuild` and `quarkus<Name>ImagePush`.
Configure a complete `imageReference`, or configure `repository` and optional `tag`; do not combine a complete reference with repository or tag components.

[[gradle-application-plugin-compatibility]]
== Compatibility, caching, and limitations

Finite `io.quarkus.application` configuration and task graphs are designed for Gradle configuration cache and Isolated Projects.
Finite build, package, model, and code-generation tasks declare inputs and outputs for Gradle up-to-date checks.
They are not currently reusable through Gradle's build cache.
Configuration-cache compatibility does not imply build-cacheability.

An up-to-date check compares a task's declared inputs and existing outputs in the current workspace and can skip execution when neither changed.
The build cache stores reusable task outputs and can restore them after a clean build or in another workspace.
These are separate mechanisms: a task can support up-to-date checks without publishing or restoring its outputs through the build cache.

The following tasks are intentionally outside configuration-cache reuse:

* `quarkus<Name>Run`;
* `quarkusApplicationDev`;
* `quarkusApplicationContinuousTest`; and
* `quarkusApplicationRemoteDev`.

Run, dev, continuous-test, and remote-dev tasks own foreground processes or live sessions rather than producing a finite file result that a later invocation could restore.
Container-image, push, deployment, and startup-optimized image actions mutate external engines, registries, or platforms.
Replaying cached local files would not reproduce those process lifecycles or external side effects, so these tasks deliberately do not use up-to-date or build-cache shortcuts for that work.

The plugin supplies the standard Quarkus application model and a Gradle sidecar used to distinguish `io.quarkus.application` and existing-plugin builds.
This does not mean every current IDE, project generator, or CLI command already selects `io.quarkus.application`.
Currently generated Gradle projects continue to use `io.quarkus`.

[[gradle-application-plugin-coexistence]]
=== Migrate with both application plugins

Applying both plugins is a migration-only shape with these boundaries:

* apply `io.quarkus` first;
* apply `io.quarkus.application` second;
* the existing plugin retains Gradle test and tooling ownership; and
* applying `io.quarkus.application` first and `io.quarkus` later is rejected.

For the task-by-task mapping, ownership restrictions, and final legacy-removal step, see xref:gradle-application-plugin-migration.adoc#gradle-application-plugin-migration-staged[Perform a legacy-first staged migration].
The `io.quarkus.application` plugin deliberately does not provide extension discovery/mutation or project/platform inspection/update tasks.
Use the xref:cli-tooling.adoc[Quarkus CLI] for listing, adding, and removing extensions and for project update workflows.

Registered task names, DSL behavior, options, configurations, and consumed variants are public user contracts for this preview.
The public Java task/model classes are also needed by Gradle and tooling boundaries, but this page does not promise that users can construct, subclass, or depend on their binary shape.

=== Troubleshooting

[cols="2,4"]
|===
|Symptom |Check

|No application build task exists
|Declare a named build; the plugin creates none implicitly.

|`assemble` does not build a named output
|Set `participatesInAssemble=true` on that named build.

|A package fails because the version is `unspecified`
|Set `project.version`, `archiveVersion`, or an explicit `outputName`.

|A copied layout launcher does not start
|Consume or archive the complete package-directory variant. Only an uber-JAR launcher is portable by itself.

|An extra Gradle property, system property, or environment variable does not affect a finite task
|Declare its exact name or prefix under `configInputs`; use ambient capture only as a temporary diagnostic bridge.

|A dev, continuous-test, or remote-dev task rejects the invocation, or a later iteration reports a configuration-cache serialization failure
|Add Gradle's `--continuous --no-configuration-cache` options.

|A native-test task is absent
|Declare a `nativeExecutable` build. Native-sources builds are not runnable.

|Image work fails before the provider starts
|Check for incomplete or conflicting image components and for another selected operation claiming the same image reference.
|===

[[gradle-application-plugin-gradle-model]]
== How the plugin works with Gradle's performance features

Gradle can avoid configuration and execution work only when a plugin describes that work without relying on hidden mutable state.
The `io.quarkus.application` plugin follows these rules for finite work such as packaging, code generation, model generation, and tests:

* Tasks declare the files and values that affect their results as inputs and declare the files they create as outputs.
  Gradle snapshots those inputs and outputs for up-to-date checks.
* A task-input value is _snapshottable_ when Gradle can capture a stable representation and compare it with a later invocation.
  Configuration-cache state must also be serializable without retaining a live `Project`, configuration, or other mutable Gradle object.
* The plugin wires task inputs and dependencies through `Provider` and `Property` values.
  This keeps values lazy: Gradle can construct the task graph without resolving a dependency, reading an output, or running work before that value is needed.
* Tasks do not reach back into a project model while they execute.
  This separation matters because the configuration cache stores the configured task graph for reuse by another invocation.
* Projects exchange artifacts through dependencies and variants instead of inspecting another project's mutable model.
  That boundary is what allows Gradle Isolated Projects to configure projects independently and, where possible, in parallel.

The same distinction matters in user build logic.
Prefer Gradle-managed paths such as `layout.buildDirectory.dir("packages")`, `layout.projectDirectory.file("config/application.properties")`, and `layout.settingsDirectory.file("shared/config")` over eagerly calculated files from `project.*` or `rootProject`.
The layout APIs preserve the location as a Gradle file value or provider that can be wired into task properties and tracked without retaining a live project model.
Accessing the current `Project` during configuration is not inherently incompatible, but capturing a `Project` or `rootProject` in a task action or provider, reading another project's model, or eagerly calculating execution-time inputs through those objects violates configuration-cache or Isolated Projects boundaries.
Pass the required value into the task through a declared `Property`, `RegularFileProperty`, `DirectoryProperty`, or file collection instead of making the task reach back into a project.

The configuration cache and Isolated Projects optimize configuration; up-to-date checks and the build cache optimize task execution.
Supporting one does not automatically provide the others.
The plugin's finite tasks declare inputs and outputs and support up-to-date checks, but are not currently reusable through Gradle's build cache.
Tasks that own a foreground process or an external mutation deliberately have different behavior, as described in <<gradle-application-plugin-compatibility,Compatibility, caching, and limitations>>.
